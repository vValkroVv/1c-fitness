# Ответы заказчика на открытые вопросы

Дата фиксации: 2026-06-22

Эти ответы являются текущими бизнес-решениями для реализации. Логически
работаем как будто сейчас момент выгрузки `2026-05-25 08:00`; июньские факты
не должны менять результат среза.

## A. Общие решения

- `A1`: финальный рабочий срез: `2026-05-25 08:00`.
- `A2`: новые импорты строятся только для клиентов из текущего финального
  `import_заявки` после всех фильтров и дедупликации. Зафиксированные финальные
  файлы лежат в корне репозитория:
  - `fitbase_active_clients_import_zayavki_20260525_0800_all_funnels.xlsx`
  - `fitbase_active_clients_plastic_cards_20260525_0800_all_funnels.xlsx`
- `A3`: клиенты, удаленные phone-dedup или другими финальными фильтрами, не
  попадают в новые файлы абонементов и услуг.
- `A4`: менеджер в новых файлах должен быть тем же, что в текущем импорте
  заявок.
- `A5`: новые файлы делаются отдельно, старые не ломаем. Исключение: исправление
  смены владельца должно распространяться на базовый пайплайн и прошлую логику.
- `A6`: тестовую загрузку в Fitbase делает пользователь. Задача пайплайна:
  пофиксить смену владельца и сформировать 2 XLSX для абонементов и 2 XLSX для
  услуг.

## B. Смена владельца и ФИО

- `B1`: смену владельца применяем строго на дату среза `2026-05-25 08:00`.
- `B2`: переоформленное членство должно быть только у нового владельца.
- `B3`: другие членства старого владельца остаются у старого владельца.
- `B4`: если у членства несколько смен владельца, берем последнего владельца на
  дату среза.
- `B5`: используем только проведенные документы; непроведенные и помеченные на
  удаление игнорируем.
- `B6`: в документе смены владельца поле `Клиент` считаем старым владельцем,
  поле `Владелец` - новым владельцем.
- `B7`: если новый владелец был в `Новые заявки` или `Реактивация`, после
  получения активного членства переводим его в `Действующие клиенты`.
- `B8`: старого владельца после передачи пересчитываем по обычным правилам.
- `B9`: если старый и новый владелец имеют один телефон, оставляем текущую
  phone-dedup логику.
- `B10`: пластиковую карту для нового владельца берем из его текущей карточки
  клиента.
- `B11`: филиал после смены владельца берем из членства/продажи.
- `B12`: финансы переданного членства в импорте абонементов показываем у нового
  владельца, даже если платил старый.
- `B13`: пары `старый владелец -> новый владелец` фиксируем в доп. отчетах, в
  XLSX не выводим.
- `B14`: обычная смена текста ФИО тоже важна, не только `Смена владельца`.
- `B15`: майские смены владельца применяются только к майскому/новому срезу,
  если попадают в cutoff и backup.

## C. Абонементы

- `C1`: переносим все исторические абонементы выбранных клиентов, включая
  закрытые.
- `C2`: включаем пробные, гостевые, недельные, подарочные и короткие
  абонементы.
- `C3`: включаем будущие/еще не активированные абонементы, если они проданы до
  cutoff.
- `C4`: непроведенные, отмененные и возвращенные продажи исключаем.
- `C5`: точный источник `contract_id` нужно выбрать по смыслу после SQL-discovery
  и сверки с прошлыми таблицами.
- `C6`: для переоформленного членства должен использоваться новый идентификатор
  членства/новой сущности, если такой источник есть.
- `C7`: `create_date` в клиентском импорте абонементов - дата заведения клиента
  в систему, как раньше в заявках по документам.
- `C8`: `payment_date` - дата оплаты текущего абонемента.
- `C9`: `activation_date` - фактическая дата начала/активации.
- `C10`: `end_date` - фактическая дата окончания.
- `C11`: если даты нет, вычисляем и фиксируем пометки в дополнительных файлах.
- `C12`: `duration` - длительность шаблона.
- `C13`: для `12+3`, подарочных месяцев и продлений писать фактические 15
  месяцев.
- `C14`: для недельных абонементов писать `0` месяцев.
- `C15`: `duration_type` всегда `месяц`.
- `C16-C19`: `freeze`, `guests`, `visits_left` считаются на момент среза/backup.
  Самое важное - субаренда; для безлимитных оставлять пусто.
- `C20`: `amount_of_payments` = сколько уже оплачено.
- `C21`: `payment_left` = весь неоплаченный остаток.
- `C22`: будущие платежи по рассрочке без просрочки тоже включаются в
  `payment_left`.
- `C23`: допустимые типы оплаты: `наличные`, `безналичные`, `сбп`.
- `C24`: шаблоны абонементов строим по всем абонементам, которые относятся к
  клиентам из зафиксированного финального `import_заявки`.
- `C25`: `Доступ в филиалах`: `Все` для мультикарт, `Продажа` для остальных.

## D. Услуги

- `D1`: услуги строятся для того же набора клиентов, что абонементы.
- `D2`: действующие услуги переносим для всех клиентов из финального
  `import_заявки`; если какой-то услуги нет среди действующих, берем до 5
  исторических примеров по клиентам из этого же XLSX. Если найдено меньше 5,
  берем максимум доступного.
- `D3`: действующая услуга - срок действия не закончился или есть остаток
  количества/посещений.
- `D4-D5`: исторический fallback берем только из клиентов финального
  `import_заявки`, не из произвольных клиентов базы.
- `D6`: если по услуге нет продаж/примеров, указать это в отчете и явно вывести
  пользователю.
- `D7`: все 51 позиции импортируются как услуги, включая доплаты, заморозки,
  утери, сертификаты и аренду.
- `D8`: для денежных/штрафных/административных услуг `duration` и `visits`
  оставлять пустыми.
- `D9`: `count` = количество услуг.
- `D10`: для пакета 12 тренировок: `count=1`, `visits_left=остаток`.
- `D11`: для разовой услуги: `visits_left=1`.
- `D12`: для солярия использовать `visits` или найденное количество минут из
  источника.
- `D13`: если услуга активируется первым посещением, но посещений не было,
  `activation_date` оставлять пустым.
- `D14`: если услуга бессрочная, `end_date` оставлять пустым.
- `D15`: продукты вроде `Пакет 12 (персональные тренировки)` идут и в импорт
  услуг, и могут продолжать участвовать в классификации воронок.
- `D16`: цена шаблона услуги = последняя фактическая цена продажи.
- `D17`: несколько product_ref с одинаковым названием объединяем в один шаблон.
- `D18-D22`: `do_enter`, `first_visit_activation`, `archive`, `category`,
  `legal_entity` заполнять по инженерному усмотрению максимально релевантно;
  после тестовой загрузки можно поправить.
- `D23`: финансовые поля услуг считать по тем же правилам, что абонементы.
