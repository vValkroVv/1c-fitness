## Почему прежняя выгрузка была неверной

### Ошибка в SQL-источнике

Прежний `sql/54_build_services_import_staging.sql` брал окончание услуги из
`dbo._Document163._Fld1482`. Для пакетов это поле обычно содержит техническую
дату `2001-01-01`, а не дату, которую пользователь видит в карточке услуги 1С.
После удаления технического значения дата превращалась в `NULL`.

Фактическая дата окончания находится в регистре сведений:

```text
dbo._InfoRg3060._Fld3064
```

Связь выполняется по документу услуги:

```text
_InfoRg3060._Fld3061RRef = _Document163._IDRRef
```

Для всех `11 295` продаж со связанным документом услуги на проверенном backup
есть ровно одна соответствующая строка `_InfoRg3060`, поэтому сопоставление
однозначно. SQL теперь отдельно считает кардинальность регистра и завершает
прогон ошибкой при `0` или более чем `1` строке на связанный документ.

### Ошибка в сборщике XLSX

Старый Python-сборщик подставлял дату продажи только историческим fallback-
строкам. У активных строк с `NULL` из ошибочного SQL `end_date` оставалась
пустой. Поэтому в принятом файле было `353` пустых дат окончания.

### Пробел в валидации

Старый валидатор не считал `end_date` обязательной и не проверял отдельно
услуги, которые действительно живы на cutoff. Книга получала `PASS`, хотя
пустые даты уже присутствовали.

## Бизнес-правило после исправления

Состав уже принятой заказчиком книги не менялся. Это важно: по согласованному
правилу в неё входят услуги с положительным остатком посещений, а для покрытия
списка из 51 услуги — также исторические примеры.

Дата окончания теперь заполняется так:

1. если есть фактическая `_InfoRg3060._Fld3064`, используется именно она;
2. если фактической даты нет, используется консервативный fallback
   `end_date = sale_date`;
3. каждый fallback записывается в отдельный аудит и никогда не считается
   доказательством живой услуги.

Результат по `522` строкам:

| источник `end_date` | строк |
| --- | ---: |
| фактическая `_InfoRg3060._Fld3064` | `343` |
| консервативный `sale_date` fallback | `179` |

Из `179` fallback-строк:

- `16` — связанные пакеты с полным остатком, которые в 1С ещё не
  активированы и поэтому не имеют фактического срока;
- `163` — продажи без фактической даты в регистре, в основном разовые,
  административные и исторические примеры.

Fallback не придумывает будущий срок и не превращает неизвестную услугу в
действующую. Все такие случаи перечислены в
`reports/services_end_date_fallbacks.csv`.

## Проверка живых услуг

Живой услугой по дате считается только строка, для которой одновременно верно:

```text
_InfoRg3060._Fld3063 <= 2026-06-30
_InfoRg3060._Fld3064 >= 2026-06-30
```

На backup найдено `19` таких услуг. Проверено, что:

- все `19` попали в итоговый XLSX;
- у всех `19` дата окончания фактическая, без fallback;
- у всех `19` дата окончания не раньше cutoff;
- все `19` принадлежат клиентам воронки `Действующие абонементы`;
- расхождений между XLSX и audit CSV нет.

Отдельный доказательный файл:


Полный аудит источника и даты для каждой из `522` строк:

## Воспроизведение

Из `end-to-end-xlsx/`:

```shell
export FITNESS_SQL_PASSWORD='...'
export FITNESS_SQL_SERVER='127.0.0.1'
export FITNESS_SQL_PORT='11434'
export FITNESS_SQL_DATABASE='FitnessRestored_20260630_macos'

scripts/run_service_end_date_fix_20260630.sh
```

Скрипт:

1. берёт принятый owner XLSX из `20260630_delivery_register_debts`;
2. пересобирает SQL-факты услуг на едином cutoff backup;
3. собирает и валидирует книгу услуг;
4. создаёт новую immutable-поставку;
5. побайтно проверяет остальные шесть XLSX;
6. запускает полный структурный валидатор.

Конфиг:

```text
end-to-end-xlsx/config/pipeline_service_end_dates_20260630.yml
```
