# Промежуточные вопросы: импорт абонементов клиентов и шаблонов

Дата перечитывания: 2026-06-21
Дата фиксации ответов заказчика: 2026-06-22

## Короткий вывод

Новый импорт абонементов нельзя делать как простое расширение текущего файла
`import_заявки`. Это отдельные XLSX:

- клиентские абонементы;
- шаблоны абонементов.

Но состав клиентов должен быть связан с текущими воронками: по переписке нужны
абонементы для тех же клиентов, которые были перенесены через заявки.

Перед этой задачей нужно исправить смену владельца, иначе абонементы будут
привязаны к старому клиенту.

## Зафиксированные бизнес-решения

- Рабочий cutoff: `2026-05-25 08:00`.
- Источник клиентов: только финальный `import_заявки` после всех фильтров и
  phone-dedup.
- Клиенты вне финального `import_заявки` не попадают в импорт абонементов.
- Менеджер: тот же, что в финальном `import_заявки`.
- Переносим все исторические абонементы выбранных клиентов, включая закрытые,
  пробные, гостевые, недельные, подарочные и короткие.
- Будущие/еще не активированные абонементы включаются, если они проданы до
  cutoff.
- Непроведенные, отмененные и возвращенные продажи исключаются.
- `create_date` в клиентском XLSX = дата заведения клиента в систему, как в
  текущем импорте заявок.
- `payment_date` = дата оплаты текущего абонемента.
- `activation_date` = фактическая дата активации.
- `end_date` = фактическая дата окончания.
- Если даты нет, ее нужно вычислить и вынести пометку в доп. отчет.
- `duration` = длительность шаблона.
- `duration_type` всегда `месяц`.
- Для `12+3`, подарочных месяцев и продлений писать фактическую длительность,
  например 15 месяцев.
- Для недельных абонементов писать `0` месяцев.
- `freeze`, `guests`, `visits_left` считаются на cutoff/момент backup.
- Для безлимитных абонементов `visits_left` оставлять пустым.
- Для субаренды `visits_left` должен быть реальным остатком.
- `amount_of_payments` = сколько уже оплачено.
- `payment_left` = весь неоплаченный остаток, включая будущие платежи по
  рассрочке.
- Типы оплаты: `наличные`, `безналичные`, `сбп`.
- `Доступ в филиалах`: `Все` для мультикарт, `Продажа` для остальных.
- Шаблоны абонементов строятся по всем абонементам, которые относятся к
  клиентам из финального `import_заявки`.
- Точный источник `contract_id` нужно выбрать по смыслу после SQL-discovery; для
  переоформленного членства использовать новый идентификатор членства/новой
  сущности, если он есть.

## Формат клиентского XLSX

Файл `Импорт_абонементы_клиентов.xlsx` содержит технические колонки:

1. `contract_id`
2. `client_id`
3. `phone`
4. `client_fio`
5. `contract_name`
6. `card`
7. `duration`
8. `duration_type`
9. `create_date`
10. `payment_date`
11. `activation_date`
12. `end_date`
13. `freeze`
14. `guests`
15. `visits_left`
16. `price`
17. `amount_of_payments`

Важно: `openpyxl` показывает `max_col=26`, потому что в шаблоне есть пустые
отформатированные колонки справа. Фактический импортный формат сейчас 20
колонок, но при генерации нужно решить, обрезать ли файл до 20 колонок или
сохранять ширину/форматирование шаблона.

## Формат шаблонов абонементов

Исходный XLSX содержит 11 технических колонок:

1. `name`
2. `price`
3. `duration`
4. `duration_type`
5. `visits`
6. `guests`
7. `freeze`
8. `first_visit_activation`
9. `archive`
10. `category`
11. `legal_entity`

По JPG нужно добавить колонку перед `name`:

```text
Доступ в филиалах
```

На скриншоте видны значения:

- `Продажа`
- `Все`
- пусто

Промежуточная проблема: это не похоже на простой список филиалов
`Гоголевский/Столица/Ровио/Промышленная`. Нужно узнать справочник значений
Fitbase для этой колонки.

## Что точно следует из переписки

- Нужны все абонементы выбранных клиентов, а не только действующие.
- Если у клиента за жизнь было 10 абонементов, нужно переносить все 10.
- Клиентские данные повторяются в каждой строке абонемента.
- Остаток посещений нужен только для ограниченных абонементов, особенно
  субаренды.
- Для безлимитных абонементов `visits_left` можно оставлять пустым, если
  Fitbase это принимает.
- Менеджер должен быть `как в заявках`, то есть скорее всего тот же
  детерминированно назначенный менеджер из текущего пайплайна, а не реальный
  продавец из 1С.
- Гостевые визиты, по словам заказчика, не используются, колонку можно
  оставлять пустой.
- По продолжительности предпочтение в месяцах, но для недельных/коротких
  абонементов это спорно.
- Нужно сделать файл, который потом проверят загрузкой в Fitbase.

## Проблема состава клиентов

В текущем part2 пайплайне есть два разных множества:

1. Полный audited stage:
   - `output/part2_20260525_0800_final/staging/final_funnel_clients.csv`
   - 72 862 клиента.

2. Финальный main XLSX после фильтров:
   - `output/part2_20260525_0800_final_combined/...import_zayavki...xlsx`
   - 64 991 строк.
   - исключены новые заявки без телефона;
   - применена дедупликация по телефону.

Решение: для импорта абонементов брать только клиентов из финального main XLSX
после фильтров и phone-dedup. Полный stage остается источником аудита, но не
источником состава клиентов для новых XLSX.

## Проблемы по cutoff и истории

Из переписки звучит `все абонементы за весь срок жизни`, но пайплайн строится
на срез:

- старый срез: `2026-04-29`;
- актуальный part2 срез: `2026-05-25 08:00`.

Решение:

- включать все исторические абонементы выбранных клиентов, которые существуют
  на дату backup/cutoff;
- будущие/еще не активированные абонементы включать, если они проданы до cutoff;
- непроведенные, отмененные и возвращенные продажи исключать.

## Проблемы по идентификаторам

Решения:

1. `contract_id` выбрать по смыслу после SQL-discovery и сверки с прошлыми
   таблицами.
2. Для переоформленного членства использовать новый идентификатор
   членства/новой сущности, если такой источник есть.
3. `client_id` должен совпадать с клиентом из финального `import_заявки`.
4. Клиентов, выкинутых phone-dedup, в этот файл не писать.

## Проблемы по датам

Зафиксированный смысл:

- `create_date`: дата заведения клиента в систему, как в текущих заявках.
- `payment_date`: дата оплаты текущего абонемента.
- `activation_date`: фактическая дата начала/активации.
- `end_date`: фактическая дата окончания.
- если дата отсутствует, вычислить и вынести пометку в доп. отчет.
- формат дат сохранять совместимым с шаблоном XLSX.

## Проблемы по duration

Решения:

1. `duration` брать как длительность шаблона.
2. Для продуктов `12+3`, подарочных месяцев и продлений писать фактическую
   длительность, например 15 месяцев.
3. Для недельных абонементов писать `0` месяцев.
4. `duration_type` всегда `месяц`.
5. Если `duration` придется вычислять, фиксировать источник/пометку в отчете.

## Проблемы по freeze/guests/visits

`freeze`:

- нужно брать остаток на cutoff/момент backup;
- источник остатка нужно найти SQL-discovery;
- если значение вычисляется, пометить это в отчете.

`guests`:

- значение на cutoff/момент backup;
- для безлимитных и случаев без гостевых оставлять пусто.

`visits_left`:

- значение на cutoff/момент backup;
- для безлимитных оставлять пусто;
- для субаренды найти реальный остаток посещений.

## Проблемы по цене и оплатам

В XLSX есть:

- `price`
- `amount_of_payments`
- `payment_left`
- `type_of_payment`

В уточнении заказчика перечислены:

- стоимость;
- сумма долга;
- способ оплаты.

Промежуточная проблема: `amount_of_payments` не был явно назван в уточнении,
но есть в шаблоне. Скорее всего:

```text
amount_of_payments = сколько оплачено
payment_left = долг / осталось оплатить
```

Решение подтверждено:

```text
amount_of_payments = сколько уже оплачено
payment_left = весь неоплаченный остаток
```

## Проблемы по рассрочке

Из трех DOCX по рассрочке:

1. Открытое членство с просрочкой:
   - пример `Барсова Анна Валерьевна`
   - продажа `20668 от 07.04.2026 13:57`
   - цена `11 990`
   - долг клиента на скриншоте `2 997`
   - есть график платежей: 5995, 2998, 2997.

2. Закрытое членство с просрочкой:
   - пример `Баженов Александр Сергеевич`
   - продажа `1160 от 16.03.2019 13:04`
   - членство истекло `15.03.2020`
   - долг клиента на скриншоте `1 661`.

3. Открытое членство без просрочки:
   - пример `Алексеева Жанна Алексеевна`
   - продажа `27916 от 12.05.2026 17:16`
   - членство активно;
   - долг `2 997`, но это будущий/непросроченный остаток.

Решения:

1. `payment_left` включает весь неоплаченный остаток, не только просроченный
   долг.
2. Будущие платежи по рассрочке без просрочки включаются в `payment_left`.
3. Допустимые типы оплаты: `наличные`, `безналичные`, `сбп`.
4. `payment_date` - дата оплаты текущего абонемента; точный выбор при нескольких
   оплатах закрыть SQL-discovery и отчетом.
5. Источник финансовых сумм должен быть проверен на трех DOCX-примерах.

## Проблемы по типу оплаты

В переписке названы три типа:

- `наличные`
- `безналичные`
- `СБПР`

Нужно SQL-discovery:

- где эти типы хранятся;
- как выглядят точные значения в 1С;
- как привести значения к трем допустимым типам: `наличные`, `безналичные`,
  `сбп`;
- как обрабатывать возврат;
- как обрабатывать неоплаченный остаток без способа оплаты.

## Проблемы по менеджеру

В текущем импорте заявок менеджер назначается детерминированно из
`config/managers_by_club.yml`, а не берется из продажи 1С.

Решения:

1. Для абонементов нужен тот же менеджер, что стоит у клиента в финальном
   `import_заявки`.
2. Клиенты вне финального `import_заявки` не попадают, поэтому отдельный
   менеджер для выкинутых phone-dedup строк не нужен.

## Проблемы по шаблонам абонементов

Решения:

1. В шаблоны включать абонементы, которые относятся к клиентам из финального
   `import_заявки`.
2. `Доступ в филиалах`: `Все` для мультикарт, `Продажа` для остальных.
3. Остальные поля без прямого бизнес-ответа закрывать SQL-discovery и
   инженерным default, если источник отсутствует.

## SQL-discovery, который нужно сделать

4. Найти фактические платежи по продаже.
5. Найти остаток долга.
6. Найти тип оплаты.
7. Найти остаток заморозки.
8. Найти остаток посещений по субаренде.
9. Найти поле/справочник доступа к филиалам.
10. Проверить named cases рассрочки по номерам продаж из скриншотов.

## Проверки после реализации

1. Все клиенты в файле абонементов должны существовать в выбранном источнике
   клиентов для заявок.
2. Все `contract_name` должны существовать в шаблонах абонементов.
3. Нет дублей `contract_id` у разных владельцев после owner-change.
4. Для безлимитных абонементов `visits_left` пустой или согласованный default.
5. Для субаренды есть остаток посещений.
6. Рассрочки из DOCX проверены отдельным report-файлом.
7. Файл проходит тестовую загрузку в Fitbase или хотя бы локальную проверку
   заголовков/обязательных полей.
