# Подготовка backup: проверки и репетиция восстановления 20.09.2026

Добавлен `end-to-end-xlsx/scripts/prepare_backup.py`. Он получает размер и SHA-256
скачанного `.bak`, читает `RESTORE HEADERONLY` и `RESTORE FILELISTONLY`, выбирает
указанный номер полного backup и выполняет `RESTORE VERIFYONLY`. `CHECKSUM`
используется только если он есть в самом backup.

`BackupFinishDate`, GUID набора и его номер остаются реальными данными источника.
Актуальность экспорта задаётся отдельно через `--effective-at` с точностью до
секунды либо `--effective-offset-days`. Например, `+1` сохраняет время вечера и
меняет календарный день. Без этих аргументов актуальность равна времени backup.

Результат подготовки хранится отдельно от очищаемой рабочей папки пайплайна:
`end-to-end-xlsx/work/prepared/<run-name>/`. В него входят JSON с заголовками,
файлами, проверкой источника, конфигурация запуска и манифест ожидаемой структуры.
Июньские количества строк и внешняя июньская сверка задолженности в новые
конфигурации не переносятся. Отдельный случай договора `151350` сохраняется как
принятое бизнесовое исключение; его можно изменить только явным параметром.
Фотографии включены в создаваемой конфигурации.

## Проверенные режимы

- `--use-existing` сверяет последнюю запись восстановления базы в `msdb`:
  GUID backup, дату завершения, исходное имя базы и номер набора. Требуется
  состояние `ONLINE` и восстановление полного backup.
- `--restore` по умолчанию восстанавливает только новую базу. Проверяются свободное место,
  отсутствие базы и занятых файлов, для всех файлов формируется отдельный `MOVE`.
  Строковые значения передаются SQL-клиенту параметрами.
- Явное сочетание `--restore --replace-existing` позволяет заменить локальную
  восстановленную базу, сохранив её физические файлы. Допустимы только соединение
  с loopback и имена `FitnessRestored_*` / `FitbasePrepareSmoke_*`. Проверяется
  история завершённого полного восстановления, отсутствие пользовательских
  сессий, точное совпадение логических файлов и типов, размещение файлов в
  проверяемом каталоге. Старое состояние и файлы записываются в аудит. Требуемое
  место считается как сумма положительного прироста файлов плюс `2 GiB`.
  Новый backup проходит все проверки до `SINGLE_USER` и `RESTORE WITH REPLACE`;
  после восстановления возвращается `MULTI_USER`. Команд `DROP` в помощнике нет.
- Существующие результаты подготовки не перезаписываются: для нового запуска
  требуется новое имя.

## Ограничение места для большого backup

При осмотре локального Mac было свободно около `53 GiB`. Только файлы
восстановленной июньской базы занимают по объявленному размеру около `84,1 GB`.
Это не позволяет заранее считать возможным второе полное восстановление рядом
с июньской базой. Для нового вечернего backup нужно проверить его собственный
`FILELISTONLY`. Можно обеспечить место для отдельной базы либо явно использовать
проверенный режим замены локальной восстановленной базы. Во втором случае
исходный июньский `.bak` сохраняется, а MDF/LDF используются повторно.
Проверка `--restore-host-dir` останавливает восстановление до записи, если
места для выбранного режима недостаточно. Существующие большие базы и файлы
в этой работе не удалялись и не заменялись.

Проверка маленькой базы подтверждает механику восстановления. Полная репетиция
бизнесового пайплайна на июньских данных документируется отдельно.
