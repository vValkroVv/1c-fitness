## Что именно исправлено

### 1. Смена владельца

Старый SQL фильтровал `_Document138._Fld764RRef`, то есть название
модификатора. Реальный вид операции хранится в `_Fld761RRef`. Из-за этого
операции с модификаторами `Переоформление бесплатное` и
`Переоформление платное абонемента на фитнес` отбрасывались.

Новая логика:

- фильтр по `_Fld761RRef = 0x9C10896C259288044EBD0A4A7A054001`;
- модификатор подключён через `LEFT JOIN` только как audit-поле;
- последняя операция выбирается по `_Date_Time DESC, _IDRRef DESC`.

SQL-аудит показал:

- фактических документов смены владельца: `5528`;
- старый фильтр принимал: `4595`;
- пропускал: `933`;
- у `861` членства менялся effective owner.

Контрольные кейсы в финальной поставке:

- `133547` принадлежит Дворжицкой Анне `000004598`;
- `144947` принадлежит Галаничевой Карине `000074154` после цепочки
  `55310 → 56656`;
- Дворжицкий Владислав и Позолотин Никита не потеряны: у них сохранены их
  собственные активные договоры `144918` и `140996`;
- все четыре клиента присутствуют в активных заявках и файле карт.

Изменение владельцев закономерно изменило производные выборки относительно
baseline:

- заявки: `39524 → 39550`;
- карты: `10907 → 11024`;
- множество реальных договоров: `45` старых строк ушли и `41` новая строка
  появилась. Все `45/41` объяснены новым effective owner и phone-dedupe;
  необъяснённых потерь нет.

### 2. Дата «Куплен»

Раньше `create_date` абонемента копировалась из заявки и означала первую
продажу клиента. Теперь для каждой реальной строки:

```text
create_date = date(Document163 sale_datetime)
```

В новом staging `100411/100411` реальных договоров имеют `create_date`, равную
дате собственной продажи; несовпадений `0`.

Контрольные примеры:

- Шулейко, `140663`: `23.09.2025`, а не `31.08.2023`;
- у восьми договоров Понедельник сохранены восемь разных дат продаж от
  `05.12.2024` до `02.06.2026`.

`payment_date` этой правкой не переопределялась как дата платёжного документа:
финансовая семантика остаётся предметом трёх прежних problem-групп.

### 3. Cycle и остатки посещений

Visit-limited классификация теперь включает ограниченную субаренду и Cycle.
Парсер понимает формы `пос`, `пос.`, `посещ`, `посещ.`, `посещение`,
`посещения`, `посещений`.

Для актуального Cycle используется отдельная размерность `_AccumRg3336`:

```text
_Fld3338_TYPE  = 0x08
_Fld3338_RTRef = 0x00000048
_Fld3338_RRRef = 0xAA9EA4BF01266AD311E8C6D3BB763918
```

Результат:

- SQL-фактов Cycle: `73`;
- клиентских строк Cycle: `72`;
- все `72` строки имеют заполненный `visits_left`;
- четыре шаблона имеют лимиты `12 / 12 / 8 / 8`;
- `64` истёкших строк Cycle получили `visits_left=0`;
- восемь активных остатков равны:
  `138687=2`, `141600=3`, `144782=3`, `144816=0`, `145361=2`,
  `147786=6`, `147787=5`, `151241=7`.

Единственный SQL-факт Cycle без клиентской строки — истёкший договор `98521`:
его клиент удалён общим phone-dedupe. Факт не потерян и имеет явную причину
`not_in_final_client_xlsx`.

### 4. Канонические шаблоны

Удалено неявное правило «последняя продажа победила».

- из `119` названий `26` имеют один наблюдаемый вариант;
- для всех `93` конфликтующих названий есть явная запись в
  `config/membership_template_canonicalization.csv`;
- новый конфликт без записи останавливает сборку;
- настроенный вариант обязан присутствовать в текущем staging;
- после обновления provenance отсутствующих source-contract ссылок `0`.

Кейс Шулейко исправлен явно: договор `140663`, цена `12990`, срок `12`, шаблон
также имеет срок `12`, а не `15`.

## Problem4: договор 151350

По `_AccumRg3336` до cutoff есть приход `8`, восемь списаний и баланс `0`.
Интерфейс 1С на скриншоте менеджера показывает `остаток (резерв) 8`. Это разные
показатели, и из backup пока не доказано, какой из них должен стать
`visits_left` FitBase.

Поэтому принято безопасное решение:

- `151350` отсутствует в clean membership;
- присутствует ровно один раз в
  `problem_4_subrent_visits_left_contract_151350_1_case_20260630.xlsx`;
- problem4 имеет те же 22 колонки, стили, фильтр и freeze panes, что problem1–3;
- никакой остаток не объявлен бизнес-истиной без согласования.

4. Истёкший Cycle `98521` не попал в клиентский XLSX из-за phone-dedupe. Если
   бизнес требует переносить `73/73` исторических Cycle, нужно решить, к какому
   клиенту привязывать договор.

   historical fallback для клиента вне final import_заявки. Это прежняя

исправлялись в этой задаче.

## Воспроизведение

Используется конфиг:

```text
end-to-end-xlsx/config/pipeline_manager_fixes_20260630.yml
```

Команда из `end-to-end-xlsx/`:

```shell
.venv/bin/python scripts/run_pipeline.py \
  --config config/pipeline_manager_fixes_20260630.yml \
  --server 127.0.0.1 \
  --port 11434 \
  --database FitnessRestored_20260630_macos
```

Пароль передаётся только через `FITNESS_SQL_PASSWORD`. Фактический runtime
этого прогона: `127.0.0.1:11434`, база
`FitnessRestored_20260630_macos`; YAML хранит переносимые значения по умолчанию.
