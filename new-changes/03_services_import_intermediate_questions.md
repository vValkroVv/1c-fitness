# Промежуточные вопросы: импорт услуг клиентов и шаблонов услуг

Дата перечитывания: 2026-06-21
Дата фиксации ответов заказчика: 2026-06-22

## Короткий вывод

Импорт услуг должен строиться отдельно от импорта абонементов. Заказчик дал
список 51 услуги и попросил:

- перенести действующие услуги этих клиентов;
- если какая-то услуга из списка не встречается как действующая, добавить хотя
  бы один исторический/недействующий пример;
- в итоге все 51 услуги должны оказаться представлены.

Текущая staging-логика абонементов не является надежным источником услуг:
многие услуги из списка есть в справочнике продуктов, но имеют `observed_sale_rows=0`
в текущем `stg_products.csv`. Это может означать, что текущий stage просто не
читает нужный источник услуг.

## Зафиксированные бизнес-решения

- Рабочий cutoff: `2026-05-25 08:00`.
- Источник клиентов: тот же финальный `import_заявки` после фильтров и
  phone-dedup, что и для абонементов.
- Переносим действующие услуги для всех клиентов из финального `import_заявки`.
- Если какой-то услуги из списка 51 нет среди действующих, добавляем до 5
  исторических примеров, но только по клиентам из финального `import_заявки`.
- Если найдено меньше 5 исторических примеров, берем максимум доступного.
- Если по услуге нет продаж/примеров, обязательно указать это в отчете и
  вывести пользователю.
- Действующая услуга: срок действия не закончился или есть остаток
  количества/посещений.
- Все 51 позиции импортируются как услуги, включая доплаты, заморозки, утери,
  сертификаты и аренду.
- Для денежных/штрафных/административных услуг `duration` и `visits` оставлять
  пустыми.
- `count` = количество услуг.
- Для пакета 12 тренировок: `count=1`, `visits_left=остаток`.
- Для разовой услуги: `visits_left=1`.
- Для солярия использовать `visits` или найденное количество минут из источника.
- Если услуга активируется первым посещением, но посещений не было,
  `activation_date` оставлять пустым.
- Если услуга бессрочная, `end_date` оставлять пустым.
- Продукты вроде `Пакет 12 (персональные тренировки)` идут и в импорт услуг, и
  могут продолжать участвовать в классификации воронок.
- Цена шаблона услуги = последняя фактическая цена продажи.
- Несколько product_ref с одинаковым названием объединяются в один шаблон.
- Финансовые поля услуг считаются по тем же правилам, что абонементы.
- `do_enter`, `first_visit_activation`, `archive`, `category`, `legal_entity`
  заполнять по инженерному усмотрению максимально релевантно; после тестовой
  загрузки можно поправить.

## Состав услуг

В `Услуги список нужных.xlsx` ровно 51 строка.

При сверке с `stg_products.csv`:

- все или почти все названия находятся в справочнике продуктов;
- много названий имеют `observed_sale_rows=0` и `observed_subscription_rows=0`;
- часть услуг имеет реальные строки в текущем источнике членств/продаж;
- `Пакет 12 (персональные тренировки)` сейчас имеет `product_class=full_subscription`
  по условному правилу для воронок;
- `Пакет 8`, `Пакет 12 ВИП`, `Пакет 8 ВИП`, `Пакет 10`, `Пакет 6`,
  `Медленный класс...` встречаются в текущих staging-продуктах как продажи или
  строки регистра.

## Конфликт с текущей классификацией продуктов

В `config/product_reclassification_decisions.csv` есть решения:

- `Пакет 12 (персональные тренировки)` считается `full_subscription` только
  если у клиента нет другого полноценного абонемента;
- субаренда была подтверждена как `other_sale`, то есть не должна считать
  клиента действующим по воронкам;
- большинство пакетов персональных тренировок подтверждены как `other_sale`.

Промежуточная проблема:

- для воронок продукт может быть `full_subscription` или `other_sale`;
- для импорта услуг этот же продукт может быть услугой;
- значит нужна отдельная классификация для `service_import`, а не повторное
  использование `product_class` из воронок.

## Проблема состава клиентов

Как и в абонементах, нужно решить источник клиентов:

1. Финальный main XLSX после фильтров и phone-dedup: 64 991 строк.
2. Полный audited stage: 72 862 клиента.

Из переписки: `по всем этим персоналиям, по которым ты перегрузил заявки`.

Решение: брать только финальный импорт заявок. Даже fallback-исторические
строки должны быть по клиентам из этого XLSX.

## Проблема активной услуги

Решение: услуга считается действующей, если срок действия не закончился или есть
остаток количества/посещений.

Технически нужно найти поля/регистры для проверки:

- дата окончания >= cutoff?
- остаток посещений > 0?
- услуга не списана полностью?
- продажа проведена и не возвращена?
- услуга активируется с первого посещения?
- услуга может быть без даты окончания?

Бизнес-ответ есть; осталось найти надежный SQL-источник для этих условий.

## Проблема исторического fallback

Заказчик сказал: если какие-то из 51 услуг неиспользованные среди действующих,
взять хотя бы один недействующий пример.

Решения:

1. Исторический fallback брать только по клиентам из финального `import_заявки`.
2. По каждой недостающей среди действующих услуге брать до 5 исторических
   примеров; если меньше 5, брать максимум доступного.
3. Если продаж/примеров нет, оставить услугу в шаблоне и обязательно указать
   это в отчете.
4. Fallback-строки помечать в отдельном отчете.

## Проблемы по `count` и `visits_left`

В клиентском XLSX есть две похожие колонки:

- `count`
- `visits_left`

Решения:

- `count` = количество услуг.
- для пакета 12 тренировок: `count=1`, `visits_left=остаток`;
- для разовой услуги: `visits_left=1`;
- для солярия: использовать `visits` или найденное количество минут;
- если услуга списана частично, остаток нужно брать из регистра/источника
  списаний.

## Проблемы по датам

Источники для этих полей нужно найти SQL-discovery:

- `create_date`: дата продажи;
- `payment_date`: дата оплаты;
- `activation_date`: дата активации услуги;
- `end_date`: дата окончания услуги.

Решения:

1. Если услуга активируется первым посещением, а посещений не было,
   `activation_date` оставлять пустым.
2. Если услуга бессрочная, `end_date` оставлять пустым.
3. Для исторического fallback можно использовать уже истекшие даты, если клиент
   входит в финальный `import_заявки`.

## Проблемы по финансам услуг

Финансовые поля похожи на абонементы:

- `price`
- `amount_of_payment`
- `payment_left`
- `type_of_payment`

Решения:

2. `price` для шаблона услуги = последняя фактическая цена продажи.
3. Разделение оплат по строкам закрыть SQL-discovery и отчетом, если услуга
   оплачена вместе с другими позициями.

## Проблемы по шаблонам услуг

Решения:

2. Цена шаблона = последняя фактическая цена продажи.
3. Для денежных/штрафных/административных услуг `duration` и `visits` пустые.
4. `do_enter`, `first_visit_activation`, `archive`, `category`, `legal_entity`

1. Найти отдельный источник продаж услуг, если текущий `stg_sales_all` не

2. Найти источник остатков посещений по услугам.
3. Найти источник списаний/посещений по услугам.
4. Найти источник активации и окончания услуги.
5. Найти источник оплат и долгов по услугам.
6. Проверить, почему многие услуги из списка имеют `observed_sale_rows=0` в

7. Проверить exact/loose matching названий, потому что есть пробелы и дубли:
