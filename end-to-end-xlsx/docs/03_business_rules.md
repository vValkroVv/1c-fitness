# Какие правила зашиты в выгрузку

Здесь собраны правила, которые влияют на состав девяти XLSX. Это не общая
документация по 1С, а описание конкретной сборки для
`Fitnes-30-06-26.bak`.

## Почему в конфиге две разные даты

```text
срез заявок и воронок:   2026-06-30 23:27:03
время окончания backup: 2026-06-30 23:27:03
срез фактов абонементов: 2026-05-25 08:00:00
срез фактов услуг:       2026-05-25 08:00:00
```

Да, майская дата рядом с июньским backup выглядит подозрительно. Это не
опечатка. В проверенной июльской сборке воронки считались на 30 июня, а SQL для
абонементов и услуг сохранил согласованный срез 25 мая. Мы вынесли обе даты в
`config/pipeline.yml`, чтобы дата не осталась незаметно зашитой внутри SQL.

Если заменить майские даты на 30 июня, набор строк изменится. Возможно, для
новой миграции это когда-нибудь и понадобится, но с эталонными файлами такой
результат уже не совпадёт.

## Как клиент попадает в воронку

Клиент берётся из `_Reference64`. Телефоны и почта собираются в одну строку на
клиента.

Дальше пайплайн смотрит историю продуктов и абонементов:

- активный основной абонемент отправляет клиента в `Действующие клиенты`;
- закончившийся основной абонемент отправляет его в реактивацию;
- если основного абонемента не было, клиент сначала считается новой заявкой.

Автоматическая классификация продуктов основана на названии и сроках. После
неё применяются ручные решения из
`config/product_reclassification_decisions.csv`. Этот CSV появился после
разбора спорных продуктов с заказчиком, поэтому заменять его свежей
автоклассификацией нельзя.

Если у абонемента менялся владелец, используется последняя проведённая операция
переоформления. При удалении дублей по телефону остаётся клиент с более поздним
выбранным абонементом.

## Что происходит с отказниками

Строки `Новые заявки / Неразобранные` в XLSX заявок не уходят. После всех
фильтров они записываются в `new_application_refusers.csv`, а затем попадают в
импорт абонементов с тегом `отказники`.

У части отказников нет ни одного абонемента. Для них создаётся техническая
строка с данными клиента и пустым `contract_id`. Это ожидаемый случай, а не
ошибка валидатора.

## Клубы, филиалы и менеджеры

```text
Коммунальная, 20       -> Фитнес Империя (Гоголевский)
Лососинское шоссе, 26 -> Фитнес Империя (Столица)
Промышленная, 10       -> Фитнес Империя (Промышленная)
Ровио, 3               -> Фитнес Империя (Ровио)
Карельский             -> Ровио, 3 -> Фитнес Империя (Ровио)
```

Карельский закрыт, поэтому в готовых файлах он всегда превращается в Ровио.
Сырое название при этом остаётся в промежуточных данных, чтобы можно было
понять происхождение строки.

Менеджер выбирается детерминированно из списка клуба в
`config/managers_by_club.yml`. При одинаковых входных данных назначение не
прыгает между запусками.

## Как строится импорт абонементов

Источником клиентов служит объединение:

- клиентов, оставшихся в финальном XLSX заявок;
- отказников, вынесенных из него.

Для каждого абонемента рассчитываются даты, срок, заморозка, гостевые визиты,
остаток посещений, цена, оплата и остаток платежа. В готовую строку также
попадают тип оплаты, менеджер и филиал продажи.

Филиал ищется в таком порядке:

1. `_Document154._Fld1116RRef`, то есть филиал документа продажи;
2. `_Document163._Fld1443RRef`, если старый абонемент не связан со строкой
   продажи;
3. филиал исходной заявки для технической строки `отказники`.

Карельский во всех трёх случаях записывается как Ровио.

## Как строится импорт услуг

В `templates/services_required.xlsx` лежит фиксированный список из 51 услуги.
Все 51 название попадает в файл шаблонов, даже если по конкретной услуге нет
клиентских строк.

Клиентские строки выбираются по продажам, связанным документам, сроку и
остатку в регистре. Филиал услуги берётся из документа продажи.

## Как отбираются три проблемных файла

Сначала строится полный импорт абонементов. Затем к его промежуточному CSV применяются
три фильтра. Только после этого спорные договоры убираются из чистого файла.

### Проблема 1: есть цена, но платёж не найден

В этот файл попадает строка, для которой одновременно верно:

- класс продукта `full_subscription`;
- дата окончания не раньше `2026-06-30`;
- `price > 0`;
- `type_of_payment = наличные`;
- источник сопоставленного платежа пуст.

На проверенном backup получилось 3 договора у 3 клиентов.

### Проблема 2: нулевая цена при найденном прямом платеже

Условия:

- класс продукта `full_subscription`;
- дата активации не позже `2026-06-30`;
- дата окончания не раньше `2026-06-30`;
- `price = 0`;
- источник платежа начинается с `direct_doc152`;
- нет проведённого непомеченного возврата `_Document131`;
- тип оплаты заполнен.

На проверенном backup получилось 41 договор у 41 клиента.

### Проблема 3: остался долг, но это не рассрочка

Условия:

- дата окончания не раньше `2026-06-30`;
- `payment_left > 0`;
- в названии абонемента нет подстроки `рассроч`.

На проверенном backup получилось 179 договоров у 178 клиентов.

## Что именно удаляется из чистой поставки

Три списка вместе содержат 223 уникальных `contract_id`. Эти строки
удаляются только из `fitbase_import_abonementy_clientov_20260630.xlsx`.

Остальные пять обычных XLSX копируются без изменений. Проблемные файлы тоже
остаются в итоговой папке, поэтому ни один спорный договор не теряется.
