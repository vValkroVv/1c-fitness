к файлу заявок. В переписке не уточнено, означает ли «актуальными» пересчёт
статусов/воронок на дату загрузки или другую корректировку. Требования прибавлять
один день ко всем датам договоров, продаж и услуг в переписке нет.

Текущая реализация следует противоположному, явно зафиксированному контракту:

```text
cutoff_at = backup_finish_at = RESTORE HEADERONLY.BackupFinishDate
cutoff_date = date(cutoff_at)
date_stamp = YYYYMMDD(cutoff_at)
```

`end-to-end-xlsx/scripts/run_pipeline.py`, метод `_apply_backup_cutoff_contract`
(с строки 209), запрещает отличающиеся даты. Последующие проверки сверяют срезы
SQL-слоёв. Контракт введён в принятую июньскую пересборку `88fe6b5` и сохранён в HEAD.

**Статус:** сдвиг +1 не готов; его нельзя незаметно включить заменой даты в YAML.
До финального прогона нужно разрешить бизнес-конфликт между пожеланием из переписки
и действующим правилом проекта. Если пожелание распространяется на сентябрь,
ожидаемая дата актуальности была бы 21 сентября при backup 20 сентября — это
интерпретация августовского запроса, а не отдельная сентябрьская команда на сдвиг.
Фактическую дату завершения backup в любом случае нельзя подменять датой импорта.

## С какой принятой версии продолжать

Актуальная июньская база для следующего прогона — **семь корневых XLSX** из
`output/20260630_delivery_funnel_labels_20260820/`, срез 30.06.2026 23:27:03.
Ссылка на девять файлов `20260630_delivery_full_cutoff` в старых инструкциях
описывает предыдущую поставку.

| Коммит | Что уже принято и должно сохраниться |
|---|---|
| `88fe6b5`, 14 июля | Единый срез по BackupFinishDate |
| `e4cf0c4`, 21 июля | Исправления по финансовой обратной связи |
| `d8402a6`, 23 июля | Деньги/долги из регистра 1С; финансовые problem-группы 1–3 возвращены в основной импорт |
| `24b1483`, 27 июля | Реальные даты окончания услуг из регистра 1С |
| `5863388`, 20 сентября | Новые подписи воронки/этапа; зафиксирован августовский фотоэкспорт и его аудит |

Для нового backup потребуется отдельная конфигурация и manifest: фактические
имя, размер, hash, БД, BackupFinishDate, пути и проверки. В текущих июньских YAML
зашиты также количества строк, сравнение с июньской таблицей задолженностей и
контрольные ID/даты услуг. Их нельзя перенести в сентябрь без адаптации.
При этом финансовые правила и исправление дат услуг уже реализованы и не должны
откатываться к старой девятифайловой сборке.

Семь файлов — принятая структура июньской поставки, а не доказанное заранее число
проблемных файлов для свежего backup. Состав исключений нужно перепроверить на новых
данных. Июньские точечные wrappers для переименования/дат услуг используют старые
поставки; свежие данные следует строить полным пайплайном.
