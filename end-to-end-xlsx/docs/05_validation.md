# Как проверяется результат

Появление десяти файлов ещё не означает, что выгрузка готова. Например, XLSX
может открываться без ошибок, но содержать старую строку из `work` или один из
спорных договоров. Поэтому проверки идут после каждого крупного этапа.

## Какие проверки запускаются

1. `preflight` проверяет базу и исходные таблицы 1С.
2. Отдельный валидатор проверяет заявки и пластиковые карты.
3. Следующий валидатор проверяет полный импорт абонементов.
4. Ещё один проверяет услуги и их шаблоны.
5. Скрипт проблемных файлов сверяет, что выбранные договоры есть в полном XLSX.
6. Последний валидатор проверяет уже собранную папку из десяти файлов.
7. `validate_manager_fixes_20260630.py` независимо проверяет бизнес-инварианты:
   владельцев, даты покупки, Cycle, Шулейко, problem4 и объяснимые регрессионные
   изменения относительно предыдущей full-cutoff сборки.

После `owner_sql` для backup от 30.06.2026 нужно отдельно запустить
`sql/audit_owner_change_20260630.sql`. Он проверяет:

- фактический enum вида операции `Смена владельца`;
- массовые source/stage счётчики;
- договор `00000133547`: владелец `000004598`, документ `00000052842`;
- договор `00000144947`: владелец `000074154`, документ `00000056656`;
- что `stg_subscriptions_all` получил тех же effective owners.

Этот audit привязан к срезу `2026-06-30 23:27:03` и на другом backup
намеренно падает, чтобы не принимать старые счётчики за новый baseline.

Последняя проверка смотрит на конкретные вещи:

- набор имён файлов;
- количество строк и колонок;
- ровно один лист в каждой книге, отсутствие формул и полностью пустых строк данных;
- 255 уникальных `contract_id` в четырёх проблемных файлах;
- отсутствие одного договора сразу в двух проблемных группах;
- отсутствие этих 255 договоров в чистом файле абонементов;
- уникальность остальных непустых `contract_id`;
- допустимые значения филиала и отсутствие пустого филиала.

Контрольные числа актуальной сборки лежат в
`reference/expected_20260630_manager_fixes_v2.yml`. Это обычный YAML,
его удобно открыть, если валидатор пишет, что ожидал другое количество строк.

## На чём проверяли сам пакет

Полный manager-fixes прогон делался 20 июля 2026 года на восстановленной копии
`Fitnes-30-06-26.bak`.

```text
database state: ONLINE
compatibility: 130
dbo source tables: 2503
required tables: 17/17
owner final_funnel_clients: 73292
backup finish / unified cutoff: 2026-06-30 23:27:03
membership facts: 101436
services facts: 50710
problem counts: 10 / 41 / 203 / 1
problem union: 255
removed from clean membership: 255
final validation: PASS
```

Все десять XLSX прошли структурную, логическую и визуальную проверку.
Дополнительно SQL-аудит показал одинаковый `cutoff_at` во всех 101 436 фактах
абонементов и 50 710 фактах услуг. Строк с продажей или платежом позже cutoff нет.

Чистый файл абонементов содержит 121 207 строк данных. Ни одного из 255
спорных договоров в нём нет.

SHA-256 самого XLSX здесь бесполезен. Внутри XLSX устроен как ZIP-архив, и при
новом сохранении в нём меняются timestamps. Два одинаковых по содержимому файла
из-за этого могут иметь разные бинарные хеши.

## Какой отчёт считать главным

После запуска отчётов несколько:

```text
work/20260630_manager_fixes_v2/reports/database_preflight.md
work/20260630_manager_fixes_v2/owner/reports/validation_report.md
work/20260630_manager_fixes_v2/imports/reports/validation_report.md
work/20260630_manager_fixes_v2/imports/reports/services_validation_report.md
work/20260630_manager_fixes_v2/reports/delivery_build.md
work/20260630_manager_fixes_v2/reports/validation_report.md
work/20260630_manager_fixes_v2/reports/validation_report.json
work/20260630_manager_fixes_v2/reports/manager_fixes_business_validation.md
```

Для финальной поставки смотрите `validation_report.md` и
`manager_fixes_business_validation.md`. Передавать файлы можно, когда оба
отчёта имеют `PASS` и списки ошибок пусты.
