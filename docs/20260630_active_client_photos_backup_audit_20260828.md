# Проверка фотографий действующих клиентов в `Fitnes-30-06-26.bak`

Дата проверки: `2026-08-28`.

## Вывод

Да, фотографии клиентов находятся внутри SQL backup и технически выгружаются
в обычные файлы изображений.

На едином срезе backup:

```text
cutoff_at = backup_finish_at = 2026-06-30 23:27:03
cutoff_date = 2026-06-30
date_stamp = 20260630
```

получен следующий результат:

| Показатель | Количество |
|---|---:|
| Действующие клиенты | 11 096 |
| Есть подтвержденное и декодируемое фото | 10 926 |
| Нет доступного фото | 170 |
| Покрытие фотографиями | 98,47% |

Для `143` из `170` карточек ссылки на фото пустые. Еще `27` карточек содержат
старую ссылку типа `Reference115`, но связанной записи с двоичными данными в
backup нет.

## Где находятся данные

Карточка клиента — `dbo._Reference64`.

Ссылки на фото находятся в составных полях:

- `_Reference64._Fld3834_RTRef/_RRRef`;
- `_Reference64._Fld9193_RTRef/_RRRef`.

Метаданные файлов находятся в двух справочниках:

- `dbo._Reference65` для типа ссылки `0x00000041`;
- `dbo._Reference115` для типа ссылки `0x00000073`.

Сами двоичные данные находятся в:

```text
dbo._InfoRg6767._Fld6769
```

Связь с файлом:

```text
_InfoRg6767._Fld6768_RTRef = тип справочника файла
_InfoRg6767._Fld6768_RRRef = ID записи файла
```

То есть backup содержит не только имена и ссылки: в `_Fld6769` присутствует
само содержимое изображений.

## Выбор рабочего фото

Для действующих клиентов подтверждены два рабочих пути:

| Путь | Клиентов | Форматы | Комментарий |
|---|---:|---|---|
| `_Fld3834 -> Reference65 -> InfoRg6767` | 6 955 | 6 821 JPG, 130 JPEG, 4 PNG | Основной файл |
| `_Fld9193 -> Reference115 -> InfoRg6767` | 3 971 | 3 966 JPG, 1 JPEG, 4 PNG | Мигрированная запись с суффиксом `- Копия` |
| Итого | 10 926 | 10 787 JPG, 131 JPEG, 8 PNG | Один выбранный файл на клиента |

Суммарный размер выбранных сериализованных BLOB — `287 038 092` байта,
примерно `273,7 MiB`.

### Размер отдельной выгрузки

Все `10 926` BLOB были потоково декодированы без сохранения фотографий на
диск. Суммарная длина реальных JPEG/PNG payload:

```text
295 289 781 bytes = 295,29 MB = 281,61 MiB
```

Расчет одного ZIP с именами вида `<ID клиента>.jpg`:

| Вариант | Размер |
|---|---:|
| ZIP без повторного сжатия изображений | `296 404 255` байт = `282,67 MiB` |
| ZIP Deflate level 6 | `287 369 380` байт = `274,06 MiB` |

JPEG/PNG уже являются сжатыми форматами, поэтому ZIP уменьшает поставку только
примерно на `3,05%`. Для передачи заказчику следует закладывать около `290 MB`
на архив и около `300 MB` с небольшим запасом под манифест и служебные файлы.
Распакованная папка может занимать немного больше логического размера из-за
размещения `10 926` отдельных файлов на файловой системе.

Для старого пути `Reference115` доступны именно записи `- Копия`. Они обычно
меньше исходного размера, поэтому перед полной выгрузкой нужно показать
заказчику несколько примеров и подтвердить, что качество подходит для импорта.

## Проверка реального извлечения

Два файла — по одному из каждого пути хранения — были декодированы в памяти,
без сохранения персональных фотографий в репозиторий.

Формат контейнера `_InfoRg6767._Fld6769`, подтвержденный на пробах:

1. первые `18` байт — служебный заголовок 1С;
2. оставшиеся байты — поток raw DEFLATE;
3. после распаковки идут длина и служебные метаданные;
4. затем находятся длина полезной нагрузки и байты изображения.

Результаты проб:

```text
Reference65: payload 14 265 bytes, signature FFD8FFE000104A4649460001, JPEG/JFIF
Reference115: payload  3 728 bytes, signature FFD8FFE000104A4649460001, JPEG/JFIF
```

В обоих случаях извлеченная длина точно совпала с длиной payload в контейнере.
Это подтверждает возможность воспроизводимой массовой выгрузки в `.jpg`/`.png`.

## Почему проверялись именно байты

В общем случае 1С умеет выносить крупные значения в отдельное файловое или
S3-хранилище. Поэтому наличие одной ссылки в SQL еще не доказывает, что фото
попало в `.bak`. Официальное описание механизма:
[Хранилище двоичных данных](https://v8.1c.ru/platforma/khranilishche-dvoichnykh-dannykh/).

В данном backup зависимость от внешнего хранилища для указанных `10 926`
фотографий исключена экспериментально: содержимое прочитано из SQL-таблицы и
превращено обратно в валидный JPEG.

## Бизнес-ответ заказчику

> Да, фото действующих клиентов можно забрать из backup. На срезе
> 30.06.2026 в базе 11 096 действующих клиентов; для 10 926 из них фото
> технически извлекается, для 170 доступного фото в backup нет. Для части
> старых карточек хранится уменьшенная копия, поэтому сначала дадим несколько
> примеров на проверку качества, затем сможем сделать полную выгрузку.

## Следующий шаг, если заказчик подтверждает выгрузку

Нужен отдельный воспроизводимый экспорт, который:

1. проверяет `BackupFinishDate` и единый cutoff;
2. строит список действующих клиентов;
3. выбирает основной путь `Reference65`, иначе мигрированную копию
   `Reference115`;
4. декодирует BLOB и проверяет сигнатуру/длину каждого изображения;
5. сохраняет фото с безопасным именем по ID клиента;
6. формирует XLSX/CSV-манифест и отдельный problem-файл для `170` клиентов без
   изображения;
7. не пишет ФИО в имя файла и не коммитит сами фотографии в Git.

Этот шаг выполнен. Итоговый ZIP и результаты проверки описаны в
`docs/20260630_active_client_photos_zip_20260828.md`.
