абонементов.

`active full сейчас + следующий/later full в статусе Контакт с клиентом`.

1. Подтвердить правило

   на текущей выгрузке это `4` строки.
2. Отдать на ручное решение `21` строку
   `started + no payment + no visits + other basis`, потому что это самый
   похожий на Попову слой без статуса `Контакт с клиентом`.
3. Отдельно решить дедупликацию `7` строк с одинаковыми датами.
4. Не удалять автоматически `11` строк с посещениями.

5. Активные `44` full-строки не похожи на возврат/блокировку: у всех есть

   Их надо решать отдельно как потерянный `price`, а не как

Главный вывод:

Математика рассрочки сейчас работает технически: `paid` берется из

Но ручные комментарии показывают, что бизнес-смысл может отличаться:

- тип оплаты в конкретной строке может быть наличным, хотя raw method указывает

- часть строк отражает служебное закрытие старого долга и новую рассрочку для

1. Подтвердить, что `payment_left` действительно надо переносить как долг в

   для всего широкого слоя `1 089` строк с `payment_left > 0`.
2. Отдельно проверить `type_of_payment` по `21` named-рассрочке вручную или через

3. Не менять автоматически все строки с `payment_left > 0` по одному
   комментарию: для named-рассрочек набор маленький, а широкий слой большой и

## Проблема 4. Конфликт по техническим raw method

Статус на `2026-06-24`: закрыто бизнес-решением. Все три технических raw method

zero-price/refund/free правил.

Прежнее бизнес-решение: эти raw method маппятся в `безналичные`:

остался пустым, не считаем проблемой технического raw method, потому что они
обнулены другими бизнес-правилами.

1. Массовое правило `технические raw method -> безналичные` оставляем.
2. Дополнительный поиск источника `сайт/эквайринг` против `наличные через
   эмулятор` по этим raw method сейчас не нужен.
3. Для пересборки XLSX отдельная кодовая правка не нужна: текущий
   `map_payment_type()` уже маппит `Для ошибок...` и
   `БАР ИП Иконников Андрей Анатольевич` в `безналичные`.
