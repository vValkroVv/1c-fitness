# Карта полей 1С -> импорт абонементов Fitbase

Здесь описано, как поля 1С превращаются в строку импорта Fitbase. Все
примеры взяты из `Fitnes-30-06-26.bak` на срез `2026-06-30 23:27:03`.

## Базовая цепочка документов

```text
_Reference64  клиент
      |
      +-- _Document163  абонемент/членство
              |
              +-- _InfoRg3060  сроки, цена и денежные поля
              |
              +-- _Document154_VT1137 -> _Document154  строка и документ продажи
                                       |
                                       +-- _Document152_VT1083 -> _Document152  платёж
                                       |
                                       +-- _AccumRg3305  движения начисления/оплаты
                                       |
                                       +-- _Document131  возврат

_Document138  может заменить исходного владельца абонемента
_Reference59  даёт пластиковую карту клиента
```

### Документ оплаты и движение оплаты

- `_Document152._Fld1080` — общая сумма платёжного документа.
- `_Document152_VT1083` — связь платежа с продажей.
- `_AccumRg3305._Fld3311` — сумма движения, распределённая на конкретную продажу.

Это разные суммы. Например, в кейсе Чекшина один `_Document152` на `9 900` связан с
двумя продажами, а `_AccumRg3305` относит по `4 950` на каждую. Значит, общую сумму
`_Document152._Fld1080` нельзя записывать в каждую связанную продажу.

## Карта 22 выходных колонок

| № | колонка Fitbase | источник 1С / правило | что именно попадает в XLSX |
| ---: | --- | --- | --- |
| 1 | `tag` | Служебная метка пайплайна, не поле 1С | Для обычных клиентов пусто; для вынесенных из заявок отказников — `отказники`. У всех 9 кейсов пусто. |
| 2 | `contract_id` | `_Document163._Number` | Внутренний номер абонемента. Если номер пуст, технический fallback — hex-ссылка `_Document163._IDRRef`. |
| 3 | `client_id` | `_Reference64._Code` | Код итогового владельца. Если есть переоформление, берётся новый владелец из `_Document138._Fld767RRef`. |
| 4 | `phone` | `_Reference64._Fld3832` | Непустые телефоны клиента, собранные в одну строку. |
| 5 | `client_fio` | `_Reference64._Description` | ФИО итогового владельца абонемента. |
| 6 | `contract_name` | `_Document163._Fld1446RRef -> _Reference72._Description` | Название продукта; затем оно сверяется с каноническим названием шаблона. |
| 7 | `card` | `_Reference59`, клиент в `_Fld3750_RRRef` при RTRef клиента | Одна непомеченная карта. Если карт несколько, их порядок задают статус, дата выдачи и ссылка. |
| 8 | `duration` | `_Document163._Fld1481`, даты `_InfoRg3060._Fld3063/_Fld3064` | Если фактический срок < 28 дней или название недельное/10-дневное — `0`. Иначе, если `_Fld1481` в диапазоне 1–60, берётся оно. Иначе округляется `duration_days / 30.4375`. |
| 9 | `duration_type` | Константа | `месяц`. |
| 10 | `create_date` | Из итогового слоя заявок | Для всех 9 кейсов это дата первой продажи клиента (`create_date_source=first_sale`). `_Reference64._Fld3822` берётся только для клиента без продаж. |
| 11 | `payment_date` | `_Document163._Date_Time` | Дата создания/продажи абонемента, а не дата `_Document152`. |
| 12 | `activation_date` | `_InfoRg3060._Fld3063` | Дата начала, с исправлением сдвига 1С на 2000 лет. |
| 13 | `end_date` | `_InfoRg3060._Fld3064` | Дата окончания, с тем же исправлением года. |
| 14 | `freeze` | `_InfoRg3060._Fld3068` | Оставшиеся дни заморозки; ноль пишется как пусто. |
| 15 | `guests` | `_InfoRg3060._Fld3069` читается в диагностику | В текущем импорте клиентов колонка намеренно пуста. |
| 16 | `visits_left` | Обычные абонементы: пусто. Ограниченная субаренда: `_AccumRg3336` | У всех 9 кейсов пусто. |
| 17 | `price` | `_InfoRg3060._Fld3070` | Цена из регистра. Её обнуляют только по явным бизнес-исключениям. Строка продажи `_Fld1160` в формуле не участвует, из-за этого появляется проблема 2. |
| 18 | `amount_of_payments` | `_InfoRg3060._Fld3072`, иногда matched payment | Если `price<=0`, то `0`. Если `_Fld3072>0`, то `min(_Fld3072, price)`. Если в названии есть `рассроч`, а `_Fld3072=0`, берётся сумма одного matched payment. В остальных случаях строка считается полностью оплаченной. |
| 19 | `payment_left` | Формула пайплайна | `max(price - amount_of_payments, 0)`. Проблема 3 показывает, что `_Fld3072` не всегда означает «уже оплачено». |
| 20 | `type_of_payment` | `_Document152._Fld1074RRef -> _Reference125._Description` | Маппинг: СБП -> `сбп`; наличные -> `наличные`; эквайринг/банк/карта/терминал/технические «для ошибок» -> `безналичные`. Если платёж не найден, но `price>0`, текущее бизнес-правило ставит `наличные` — это и создаёт проблему 1. |
| 21 | `manager` | `config/managers_by_club.yml` | Не поле 1С. Менеджер выбирается из списка филиала по стабильному правилу. |
| 22 | `филиал` | `_Document154._Fld1116RRef -> _Reference105` | Филиал продажи. Если нет связанной продажи, fallback — `_Document163._Fld1443RRef`. Карельский нормализуется в Ровио. |

## Филиал продажи не равен филиалу регистрации клиента

В выходную колонку `филиал` пишется филиал продажи, а не организация из карточки
клиента:

| смысл | поле |
| --- | --- |
| организация/возможный филиал регистрации клиента | `_Reference64._Fld3831RRef -> _Reference105` |
| филиал конкретной продажи | `_Document154._Fld1116RRef -> _Reference105` |

Различие видно прямо на тестовых кейсах:

| contract_id | организация клиента | филиал продажи / в XLSX |
| --- | --- | --- |
| `00000140456` | Фитнес Империя (Гоголевский) | Фитнес Империя (Столица) |
| `00000133458` | Фитнес Империя (Промышленная) | Фитнес Империя (Ровио), сырое значение Карельский |
| `00000134111` | Фитнес Империя (Промышленная) | Фитнес Империя (Ровио) |
| `00000146001` | Фитнес Империя (Гоголевский) | Фитнес Империя (Промышленная) |

Если Fitbase нужен филиал регистрации, его нужно выгружать отдельно. Текущая колонка для этого не
подходит.

## Как сейчас выбирается один matched payment

Пайплайн сначала строит direct-связь:

```text
_Document163
  -> _Document154_VT1137 (_Fld1148_RTRef=0x000000A3)
  -> _Document154
  -> _Document152_VT1083 (_Fld1087_RTRef=0x0000009A)
  -> _Document152
```

Если direct-платёжа нет, ищется платёж того же клиента в окне ±14 дней. Из кандидатов берётся
один `TOP 1` платёж по такому порядку:

1. direct выше fallback;
2. распознаваемый способ оплаты выше неизвестного;
3. та же дата выше;
4. меньше разница во времени;
5. сумма ближе к `_Fld3072` или `_Fld3070`;
6. более поздний платёж.

Такого выбора хватает для `type_of_payment`, но не для общей оплаченной суммы: в проблемах 2 и 3
часто находится несколько `_Document152`.

## Какие источники сейчас не участвуют в формуле денег

`_Document154_VT1137._Fld1160` и `_AccumRg3305._Fld3311` есть в диагностике, но в формулу
`price/amount_of_payments/payment_left` они не входят. Сейчас формула берёт `_InfoRg3060._Fld3070/_Fld3072`.
Из-за этого и появились три группы из этого пакета.
