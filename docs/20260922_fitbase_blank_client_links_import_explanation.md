# Уточнение причины 767 заявок без связи с карточкой

**Продолжение с полной поимённой сверкой текущих 716:** [подробный разбор причин и примеров](20260922_fitbase_remaining_716_root_causes.md). Установлено 715 исходных клиентов и одна дополнительная заявка; отдельно выявлены две ссылки на карточки других исходных клиентов. Ниже сохранён ход уточнений и более ранние срезы.

## Новая информация от заказчика

22.09.2026 заказчик передал объяснение исполнителя переноса:

- список клиентских карточек формировали из `fitbase_import_abonementy_clientov`;
- заявки импортировали из `fitbase_active_clients_import_zayavki`;
- если клиент присутствовал только в файле заявок, его заявка создавалась без карточки;
- существующие карточки 57 клиентов, по сообщению исполнителя, уже привязали к заявкам.

Число 57 является сообщением исполнителя. Список этих клиентов и результат исправления по каждому ID пока не сверены в интерфейсе. Нельзя считать 57 подтверждённой частью исходной выборки 767 или автоматически объявлять остаток равным 710.

## Что установлено по исходной выборке

Повторная локальная проверка `output/20260922_fitbase_live_audit/blank_client_links/cohort.json` и `output/20260922_fitbase_live_audit/source.sqlite` подтвердила:

| Группа исходных 767 заявок | Всего | Действующие по исходной воронке | Реактивация |
| --- | ---: | ---: | ---: |
| Есть строки в переданном файле абонементов; ранее в живом интерфейсе найдена карточка с теми же ФИО, телефоном и пластиковой картой | 50 | 14 | 36 |
| Нет строк в переданном файле абонементов | 717 | 0 | 717 |
| Всего | 767 | 14 | 753 |

До сообщения об исправлении все 767 заявок были найдены в живом интерфейсе в фильтре «Клиент не создан», с кнопкой «Создать клиента». Это свидетельствует об отсутствии связи на момент наблюдения, а не об удалении 767 карточек.

Для 50 клиентов наличие карточки было подтверждено независимо от наличия заявки. Например, у Беланиной Елены Юрьевны существовала карточка 115523, но заявка 39318 не была связана с ней. Это была реальная проблема привязки на момент проверки. После сообщения об исправлении требуется повторная проверка именно этих связей.

Для 717 клиентов объяснение исполнителя согласуется с составом переданных файлов: заявка имелась, строк абонементов не было. Если карточки действительно создавали исключительно по файлу абонементов, отсутствие карточки у такого клиента объясняется выбранным правилом импорта. Это не доказательство потери карточки, уже созданной в Fitbase. Оценка полноты переноса зависит от требования: должны ли были появиться карточки всех клиентов файла заявок, включая клиентов без передаваемых абонементов. Их присутствие в заявках само по себе не создаёт строку в файле абонементов.

## Почему этих клиентов нет в нашем файле абонементов

После дополнительного вопроса заказчика проверены не только импортные файлы, но и исходный и переклассифицированный staging прогона `20260921_final_v2`, конечная воронка, подготовленные факты абонементов и ранее сохранённая исключённая история. История у обеих клиенток в исходной базе была. Предыдущая формулировка об их отсутствии в импортном файле без объяснения этой причины была неполной.

У обеих найден продукт **«Подарочный сертификат 1 месяц безлимитного фитнеса»**, код `00000001464`:

| Клиент | Номер договора в источнике | Начало | Окончание |
| --- | --- | --- | --- |
| Быстревская Ирина Владимировна | 00000133590 | 30.03.2025 | 29.04.2025 |
| Лукина Анна Леонидовна | 00000150387 | 17.05.2026 | 16.06.2026 |

Точная цепочка исключения:

1. В `raw/staging/stg_subscriptions_all.csv` оба договора имеют исходный класс `unknown_review_required`.
2. Правило в `config/product_reclassification_decisions.csv` относит этот сертификат к `full_subscription`. В `owner/staging/stg_subscriptions_all.csv` оба договора уже имеют этот класс и признак завершения до среза. Поэтому обе клиентки присутствуют в реактивации и конечном файле заявок.
3. SQL сборки абонементов читает исходный staging. Фильтр допускает `full_subscription`, `trial_or_guest` и продукты с субарендой в названии. Исходный класс сертификатов не проходит фильтр. См. [SQL, строка 344](../end-to-end-xlsx/sql/31_build_membership_import_staging.sql#L344).
4. В `membership_import_facts.tsv` нет ни одной строки с ID этих клиенток. Таким образом, отбор произошёл до сборки XLSX, а не при загрузке в Fitbase. Само истечение срока не является непосредственным условием данного исключения: причина — различие классификации между двумя ветками подготовки.
5. По сообщению исполнителя, клиентские карточки создавали из файла абонементов. Поэтому отсутствие там этих клиенток привело к отсутствию карточек, хотя заявки были переданы.

Это известная граница подготовки данных, зафиксированная ещё в [аудите охвата от 21 сентября](20260921_membership_coverage_audit.md). В документах того дня записано решение сохранить июньские правила, а исключённую историю приложить отдельным контрольным отчётом. Такое решение по составу истории не тождественно решению не создавать клиентские карточки.

В полной контрольной группе **766 клиентов и 1 806 договорных записей**, все договоры закончились до среза. Повторное сопоставление по исходным ID установило: **все 717 клиентов без абонементов из исследуемых 767 входят в эту группу**, у них **1 724 договорные записи** в исключённой истории. Необъяснённых ID при этом сопоставлении — **0**. Остальные 49 клиентов контрольной группы не входят в исходную выборку 767; их текущее состояние этим сопоставлением не установлено.

Важно для фактической передачи: загруженный `20260921_fitbase_for_customer.zip` содержит семь XLSX и архив фотографий, но не содержит `excluded_history.csv`. Это подтверждено [описанием компактного комплекта](20260921_customer_files_only.md). Контрольный CSV в любом случае не являлся импортным файлом абонементов.

Чтобы восстановить полноту именно клиентских карточек, необходим отдельный охват клиентов из заявок, у которых нет строк абонементов. Добавление их исторических договоров — отдельный вопрос состава импорта; вымышленные абонементы для создания карточек не нужны. В рамках этой проверки данные и правила сборки не изменялись.

Повторно извлечённые строки и проверки сохранены в [source_exclusion_root_cause.json](../output/20260922_fitbase_live_audit/blank_client_links/source_exclusion_root_cause.json).

## Подарочные сертификаты: повторная живая проверка 22 сентября, 17:43–17:46 МСК

Среди исходных 717 клиентов без строк абонементов найдено **72 клиента** с продуктом «Подарочный сертификат 1 месяц безлимитного фитнеса». У каждого по одной такой договорной записи. Все 72 относятся к реактивации; действующих по исходной воронке — 0.

Все 72 повторно найдены в Chrome в текущих заявках с фильтром «Клиент не создан» и кнопкой «Создать клиента». Сопоставление выполнено по точному телефону, с единственной найденной заявкой для каждого телефона и совпадением клуба с исходником. Полученные ID заявок сохранены отдельно.

| Клуб | Клиентов с подарочным сертификатом, повторно найденных без привязки | Текущий счётчик непривязанных заявок реактивации |
| --- | ---: | ---: |
| Гоголевский | 35 | 73 |
| Промышленная | 13 | 15 |
| Ровио | 12 | 615 |
| Столица | 12 | 13 |
| **Всего** | **72** | **716** |

В двух воронках действующих, где ранее было 14 случаев (Гоголевский, ID 7; Ровио, ID 13), тот же фильтр теперь показывает «Ничего не найдено».

Число **710**, полученное как `767 − 57`, не подтверждено текущими счётчиками: в четырёх проверенных воронках реактивации сумма равна **716**. Это новый срез интерфейса, а не поимённо восстановленный остаток исходной выборки после исправлений. Нельзя утверждать, что 72 относятся к точно определённому множеству «710», пока состав 57 исправлений не сопоставлен. Можно утверждать, что все эти 72 всё ещё находятся среди текущих непривязанных заявок.

Для проверки сертификатов прочитаны все страницы реактивации Гоголевского, Промышленной и Столицы, а также первые четыре страницы Ровио: уже на них найдены все 72 искомых клиента. Общие 716 взяты из счётчиков UI; полный построчный пересбор этого нового остатка в этой проверке не выполнялся.

Детальный список с исходными ID, телефонами, номерами договоров и живыми ID заявок: [gift_certificate_remaining.json](../output/20260922_fitbase_live_audit/blank_client_links/gift_certificate_remaining.json).

## Как меняется дальнейшая проверка

Поиск карточек по телефону и ФИО был нужен, чтобы различить существующую непривязанную карточку и отсутствие карточки. До объяснения исполнителя нельзя было считать все пустые значения CSV одной и той же проблемой.

Теперь приоритет — сопоставить заявленные 57 исправлений с конкретными ID заявок и карточек, убедиться в исправлении 14 случаев действующей воронки из исходной выборки и зафиксировать оставшихся клиентов, исключённых из создания карточек правилом импорта. Продолжение массового поиска по ФИО остальных 717 не требуется для объяснения причины; оно может иметь смысл только для проверки отдельных неоднозначных совпадений.

Поиск по ФИО был завершён для 59 из 717, а не для всей группы. Неоконченные поиски не следует описывать как доказанное отсутствие карточек. Ранее обнаруженные кандидаты с другим телефоном/ФИО не включены в число 50 подтверждённых карточек.

В Fitbase изменений со стороны аудитора не выполнялось.
