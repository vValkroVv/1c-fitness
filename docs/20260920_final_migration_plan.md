## 1. Согласованные правила

Уточнение от 22.09.2026: во всех числовых полях файлов шаблонов абонементов
и услуг используется формат `General`, без группировки тысяч и обязательных
нулевых копеек. Значения остаются числами, дробные суммы не округляются.
Правило включено в сборщики; [проверка и отдельная копия шаблонов 21 сентября](20260922_template_plain_numbers.md).

20 сентября заказчик ответил: «Вечер 20 делать как вечер 21». Для сегодняшнего
запуска используем **BackupFinishDate + 1 сутки с сохранением часов, минут и
секунд**. Например, `2026-09-20 22:17:05` → `2026-09-21 22:17:05`.
Если понадобится другое точное время, оно задаётся через `--effective-at`.
Момент `23:59:59` автоматически не подставляется.

Две даты имеют разный смысл:

```text
backup_finish_at = фактический RESTORE HEADERONLY.BackupFinishDate
cutoff_at = effective_at (согласованная дата и время актуальности)
cutoff_date = date(cutoff_at)
date_stamp = YYYYMMDD(cutoff_at)
```

Если явное время или смещение не заданы, сохранён прежний режим:
`cutoff_at = backup_finish_at`. Это уточнение пользователя от 20.09 заменяет
прежний безусловный запрет на отличающийся cutoff. Для клиентов, воронок, карт,
абонементов, услуг, шаблонов, problem-файлов и фото действует **один cutoff**.
Несовпадение дат отдельных слоёв останавливает сборку.

Срез означает пересчёт состояний по доступным данным backup. Даты продаж,
платежей, начала и окончания договоров и услуг не сдвигаются на сутки.
Операции, которых нет в backup, не добавляются. Имеющиеся в backup документы
с будущей датой отбираются по общему времени актуальности во всех слоях.
Время задаётся в локальном времени исходной SQL-базы, как в HEADERONLY;
скрытого преобразования в UTC нет.

## 4. Основной запуск

**Уточнение пользователя 21 сентября: нужны обе восстановленные базы.**
Замена июньской SQL-копии была ошибкой исполнения. Июньский backup
восстановлен отдельно как `FitnessRestored_20260630_original`.
Сентябрьские данные пока остаются в `FitnessRestored_20260630_macos`;
дата в этом техническом имени не соответствует содержимому.
Для будущих backup создавать отдельную базу без `--replace-existing`.
Команда ниже сохранена только как история уже выполненной операции.
Обе базы проверены: `ONLINE`, `MULTI_USER`, UUID и даты backup совпадают
с соответствующими исходниками. Свободно около 24 GiB.
Подробности: [восстановление обеих баз](20260921_both_databases.md).

21 сентября выполнено восстановление нового backup вместо локальной июньской
SQL-копии. Имя `FitnessRestored_20260630_macos` сохранено как техническое;
база теперь содержит сентябрьские данные, проверенные по UUID и HEADERONLY.
Ниже выполненная команда подготовки и восстановления. XLSX и фото этим запуском
не формировались.

```bash
python3 scripts/run_fitbase_migration.py \
  --backup-file data/Fitnes-20-09-26.fast.bak \
  --backup-sql-path /backup/Fitnes-20-09-26.fast.bak \
  --database FitnessRestored_20260630_macos \
  --run-name 20260920_final \
  --effective-offset-days 1 \
  --restore --replace-existing \
  --restore-host-dir mssql-macos/data \
  --prepare-only
```

Режим замены включается только явным `--replace-existing`. До замены должны
пройти проверки нового backup; скрипт проверяет локальное подключение, историю
полного восстановления, отсутствие пользовательских SQL-сессий, соответствие
логических файлов и место под рост файлов + 2 GiB. Физические MDF/LDF
используются повторно. Прежняя история и пути сохраняются в аудите.
Подготовка завершилась со статусом **PASS**, база вернулась в `ONLINE`
и `MULTI_USER`. Метаданные сохранены
в `end-to-end-xlsx/work/prepared/20260920_final/backup_metadata.json`.
Каталог этого запуска уже занят: команду подготовки с тем же `--run-name`
повторно не выполнять. Для нового запуска через `--use-existing` нужно новое
имя запуска. Результаты: [восстановление сентября](20260921_september_restore.md).

Для уже восстановленного сентябрьского backup использовать
`--database FitnessRestored_20260630_macos --use-existing` с новым `--run-name`,
без `--restore`, `--replace-existing` и `--restore-host-dir`.
UUID, время и исходное имя базы проверяются по последнему восстановлению
в `msdb`. Июньская `FitnessRestored_20260630_original` для сентябрьского
переноса не используется.

Для точного времени заменить `--effective-offset-days 1` на, например:

```text
--effective-at "2026-09-21 22:17:05"
```

Варианты времени взаимоисключающие. `--prepare-only` выполняет только
подготовку и проверки. Без `--restore`/`--use-existing` он не утверждает, что
база уже готова. Полный запуск всегда требует одного из этих двух режимов.

Подготовка сохраняет в `end-to-end-xlsx/work/prepared/<run-name>/`:

- `backup_metadata.json`: SHA-256, размер, HEADERONLY, FILELISTONLY, VERIFYONLY,
  реальное время backup, выбранное время актуальности и история восстановления;
- `pipeline.yml`: конфигурация для этого backup;
- `expected.yml`: принятые структура/филиалы/инварианты без июньских счётчиков.

Далее выполняются: preflight → SQL клиентов → CSV и переклассификация →
заявки/карты → абонементы → услуги → problem-файлы → сборка поставки → проверки
XLSX → фото → проверка архива → хеши поставки → `READY.txt`.
