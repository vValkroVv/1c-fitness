# Проблема 3. Остался долг, но в названии нет «рассрочки»

## В чём проблема

На срезе 30 июня в этой группе 203 договора 202 клиентов.

Строка попадает в эту группу, если:

```text
end_date >= 2026-06-30
payment_left > 0
contract_name does not contain "рассроч"
```

Фильтр специально сделан широким. Все 203 долга не обязаны быть ошибками. Здесь собраны строки, в которых нужно проверить смысл `_Fld3072`.

## Массовая проверка всех 203 строк

Для каждой строки мы взяли:

- `price = _InfoRg3060._Fld3070`;
- текущий `amount_of_payments = _InfoRg3060._Fld3072`;
- текущий `payment_left = price - _Fld3072`;
- все уникальные `_Document152`, связанные с целевой продажей;
- движения `_AccumRg3305` по этой продаже.

Результат:

| проверка | rows из 203 |
| --- | ---: |
| есть direct-платежи к целевой продаже | 203 |
| сумма direct-платежей примерно равна текущему `payment_left` | 197 |
| `direct_sum + _Fld3072` примерно равно `price` | 197 |
| сумма direct-платежей равна `_Fld3072` | 107 |
| один уникальный платёж | 110 |
| два или три платежа | 93 |
| сумма direct-платежей не равна ни `_Fld3072`, ни текущему `payment_left` | 6 |

Самое заметное совпадение:

```text
в 197 строках пайплайн называет «долгом» сумму, которая уже набирается direct-платежами
```

Есть и ловушка: 107 строк попадают сразу в два равенства. Например, при цене `10 990` сумма `5 495` может быть и оплатой, и остатком. По одним цифрам их не различить. Поэтому в архиве есть контрольный кейс Ойева.

## Почему текущая формула даёт спорный результат

Сейчас для любого абонемента с `price>0` и `_Fld3072>0` выполняется:

```text
amount_of_payments = min(_InfoRg3060._Fld3072, price)
payment_left       = price - amount_of_payments
```

Сумма всех `_Document152` и `_AccumRg3305` в формуле не участвует. Один matched payment нужен только для типа оплаты. Для абонементов со словом `рассрочка` он иногда подставляется в сумму. В этой группе такого правила нет.

## Что проверить

1. Что именно означает `_InfoRg3060._Fld3072`: «оплачено», «осталось», сумму текущего этапа или другую величину?
2. Хранит ли `_AccumRg3305 RecordKind=0` распределённую оплаченную сумму по конкретной `_Document154`?
3. Как учитывать возвраты, сторно и коррекции в `_AccumRg3305`, чтобы `paid` не был завышен?
4. Подтверждаете ли, что по Бандзерук правильный остаток — `3 997`, а не `11 993`?
5. Подтверждаете ли, что по Ойеву реально осталось `5 495`?
6. Подтверждаете ли, что платёж Чекшина на `9 900` должен быть распределён по `4 950` на две продажи?
7. Какой смысл имеет `_InfoRg3060._Fld5963`? В трёх кейсах там `8`, `5`, `3`, что не равно фактическому числу платёжных документов.

## Если `_AccumRg3305` хранит оплату

Если `_AccumRg3305 RecordKind=0` действительно хранит распределённую оплату, правило можно собрать так:

```text
price = сумма начисления по продаже
paid  = чистая сумма распределённых оплатных движений по той же продаже
left  = max(price - paid, 0)
```

Перед внедрением нужно обязательно проверить:

- знак `RecordKind` во всех типах операций;
- возвраты и сторно;
- общие платёжи, распределённые между несколькими продажами;
- переплаты;
- переоформление владельца;
- операции через эмулятор/вспомогательную продажу.

На трёх выбранных кейсах результат должен быть таким:

- Бандзерук должна измениться;
- Ойев должен остаться без изменений;
- Чекшин должен остаться без изменений и не получить двойную оплату.
