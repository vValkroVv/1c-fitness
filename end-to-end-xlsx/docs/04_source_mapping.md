# Откуда берутся поля

У таблиц 1С в SQL технические имена: `_Reference64`, `_Document163` и так
далее. Номера зависят от конфигурации. Эта карта проверена для
`Fitnes-30-06-26.bak`; на другой базе сначала нужно заново сверить структуру.

## Клиент и контакты

| Что нужно для Fitbase | Поле в 1С |
| --- | --- |
| ссылка на клиента | `dbo._Reference64._IDRRef` |
| внутренний номер | `dbo._Reference64._Code` |
| ФИО | `dbo._Reference64._Description` |
| дата создания карточки | `dbo._Reference64._Fld3822` |
| телефон | `dbo._Reference64._Fld3832` |
| организация клиента | `dbo._Reference64._Fld3831RRef -> dbo._Reference105` |
| email | `dbo._InfoRg5255._Fld5257`, клиент в `_Fld5256RRef` |

В некоторых датах 1С год сдвинут на 2000 лет. Например, 4026 означает 2026.
SQL исправляет это до выгрузки.

## Клуб и филиал

| Что ищем | Поле в 1С |
| --- | --- |
| справочник организаций | `dbo._Reference105` |
| клуб документа абонемента | `dbo._Document163._Fld1443RRef` |
| клуб платёжного документа | `dbo._Document152._Fld1051RRef` |
| филиал продажи | `dbo._Document154._Fld1116RRef` |

Организации сводятся к четырём филиалам Fitbase. Исторический Карельский
попадает в Ровио.

## Продукт и абонемент

| Что ищем | Поле или таблица в 1С |
| --- | --- |
| справочник продуктов | `dbo._Reference72` |
| документ абонемента или услуги | `dbo._Document163` |
| держатель | `_Document163._Fld9152RRef -> _Reference64` |
| плательщик, если нет держателя | `_Document163._Fld1447_RRRef` при клиентском RTRef |
| продукт | `_Document163._Fld1446RRef -> _Reference72` |
| сроки, статус и остатки | `dbo._InfoRg3060`, связь через `_Fld3061RRef` |
| статус брони | `_InfoRg3060._Fld5960RRef -> _Reference5062` |

Сначала продукт получает класс по названию и фактическим срокам. Потом класс
может быть заменён решением из
`config/product_reclassification_decisions.csv`.

## Смена владельца абонемента

| Что ищем | Поле в 1С |
| --- | --- |
| документ переоформления | `dbo._Document138` |
| абонемент | `_Fld763RRef` |
| старый клиент | `_Fld762RRef` |
| новый клиент | `_Fld767RRef` |
| вид операции | `_Fld761RRef`; `9C10896C259288044EBD0A4A7A054001` (`_Enum186`, order `5`) = `Смена владельца` |
| модификатор операции | `_Fld764RRef` |

Документ отбирается по виду операции `_Fld761RRef`, а не по названию
модификатора. Модификаторы `Переоформление бесплатное` и
`Переоформление платное абонемента на фитнес` также являются сменой владельца.

Берётся последняя проведённая и непомеченная смена по абонементу на единый cutoff.
Сортировка: `_Date_Time DESC, _IDRRef DESC`. В
промежуточных файлах остаются оба владельца: исходный и итоговый. Это помогает
разобрать строку, если переоформление выглядит странно.

## Продажа, оплата и возврат

| Что ищем | Таблица в 1С |
| --- | --- |
| документ продажи | `dbo._Document154` |
| строки продажи | `dbo._Document154_VT1137` |
| документ оплаты | `dbo._Document152` |
| строки связи оплаты с продажей | `dbo._Document152_VT1083` |
| способ оплаты | `dbo._Reference125` |
| тип операции | `dbo._Reference101` |
| возврат | `dbo._Document131` |

Строка продажи связывается с `_Document163` через пару RTRef/RRRef. Оплата
связывается с продажей через `_Document152_VT1083`. В промежуточный CSV
записывается способ сопоставления платежа; он нужен для первых двух проблемных
файлов.

## Пластиковая карта

| Что ищем | Поле в 1С |
| --- | --- |
| справочник карт | `dbo._Reference59` |
| клиент карты | `_Reference59._Fld3750_RRRef` при клиентском RTRef |

Помеченные карты не берутся. Если действующих карт несколько, скрипт выбирает
одну по фиксированной сортировке: состояние, дата выдачи и ссылка карты.

## Остаток посещений и услуги

| Что ищем | Таблица или поле в 1С |
| --- | --- |
| движения посещений | `dbo._AccumRg3336` |
| ссылка на документ абонемента/услуги | `_Fld3337_RRRef` |
| продажа услуги | `_Document154 + _Document154_VT1137` |
| документ услуги | `_Document163` |
| оплата услуги | `_Document152 + _Document152_VT1083` |

По регистру считаются приход, расход и итоговый остаток. Услуга считается
активной, если остаток положительный или связанный документ ещё не закончился.

## Таблицы, которые создаёт пайплайн

Всё промежуточное SQL хранится в схеме `fitbase_part2`:

- 13 таблиц с клиентами, продажами, картами и воронками;
- `membership_import_facts`;
- `services_import_facts`.

Эти таблицы можно удалить после выгрузки. Таблицы `dbo` скрипт не изменяет.
