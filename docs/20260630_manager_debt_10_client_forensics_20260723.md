# Судебный разбор 10 клиентов из отчёта задолженностей менеджера

- Дата анализа: `2026-07-23`
- Backup cutoff: `2026-06-30 23:27:03`
- Менеджерский файл: `Задолженности клиентов 30.06.2026.xlsx`
- Исследуемая поставка: `output/20260630_delivery_manager_debts_applied/`

## Ограничение задачи

Это только read-only анализ расхождений. Итоговые сборки, XLSX и код
формирования поставки в рамках этого исследования не изменялись.

`FitnessRestored_20260630_macos`.

## Главный вывод

Числа менеджера не являются внешними ручными данными: основные финансовые
значения действительно находятся в том же backup 1С, но наш пайплайн читал
не тот источник и неверно интерпретировал одно из полей.

Подтверждённая схема отчёта 1С:

```text
Продано =
    сумма строки конкретной продажи
    _Document154_VT1137._Fld1160

Оплачено на cutoff =
    сумма распределённых на эту продажу оплат
    _AccumRg3305._Fld3311 при RecordKind = 0

Задолженность на cutoff =
    Σ(_AccumRg3305._Fld3311 при RecordKind = 1)
    -
    Σ(_AccumRg3305._Fld3311 при RecordKind = 0)
```

В начислениях `RecordKind = 1` могут присутствовать корректировки с
отрицательной суммой. Поэтому задолженность нельзя надёжно получить только
как `цена - один найденный платёж`.

Наш старый расчёт делал другое:

```text
price = _InfoRg3060._Fld3070
paid = _InfoRg3060._Fld3072
payment_left = price - paid
```

На исследованных данных `_Fld3072` почти всегда означает остаток долга, а не
оплаченную сумму. В результате оплачено и долг часто менялись местами.

## Что видно по всем 192 найденным договорам

- `192 = 1` договор из problem1 и `191` договоров из problem3.
- Во всех `192` случаях менеджерское `Продано` совпало с
  `_InfoRg3060._Fld3070` и суммой строки продажи
  `_Document154_VT1137._Fld1160`.
- В `190` из `191` строк problem3 менеджерская `Задолженность` совпала с
  `_InfoRg3060._Fld3072`, которое пайплайн называл кандидатом на оплату.
- Разбиение `191` строки problem3:
  - `89` строк выглядели корректно только потому, что оплачено и долг были
    равны;
  - `65` строк — точная перестановка значений «оплачено» и «долг»;
  - `36` строк — долг совпадает с `_Fld3072`, но поле «Оплачено» менеджерского
    отчёта требует суммирования нескольких оплат либо содержит значение,
    отсутствующее в backup;
  - `1` строка — корректировка в регистре, из-за которой одного
    `_Fld3072` недостаточно.
- У `38` из `192` выбранных строк менеджерского файла не выполняется
  `Продано - Оплачено = Задолженность`. Поэтому три колонки отчёта нельзя
  безусловно считать одним арифметическим состоянием на одну дату.

## Почему выбраны именно эти 10 клиентов

Выборка покрывает разные причины расхождений: отсутствие платежа, корректировку,
несколько оплат, отсутствие телефона, общий платёж на две продажи, точную
перестановку полей, разницу в два рубля, сумму из нескольких строк
распределения и значения менеджерского отчёта, которых нет в snapshot backup.

## Подробно по каждому клиенту

### 1. Бабаров Юрий Александрович, договор `00000152426`

Продажа `00000035181` от `2026-06-30 17:23:11`.

В `_AccumRg3305` есть только начисление `10990`; платежных документов и
движений оплаты до cutoff нет. Поэтому долг `10990` из отчёта менеджера
полностью подтверждается backup.

Старая выгрузка приняла `_Fld3072 = 10990` за оплату и получила нулевой долг.
Менеджерское `Оплачено = 10990` в этом backup не воспроизводится и одновременно
нарушает арифметику самого отчёта:
`10990 - 10990 != 10990`.

### 2. Дмитрий, договор `00000148035`

Продажа `00000015279` от `2026-03-13 11:07:45`.

В регистре находятся:

```text
начисление             11990
корректировка          -2997
оплата                  5995
остаток: 11990 - 2997 - 5995 = 2998
```

Корректировка записана `2026-04-17 16:30:20` регистратором типа
`0000009F`. Именно она объясняет менеджерский долг `2998`.
`_Fld3072 = 3997.11` здесь не является достоверным ни полным остатком, ни
суммой оплаты.

Менеджерское `Оплачено = 11989` на `5994` больше оплаты, присутствующей в
snapshot. Эта дополнительная сумма в backup не найдена.

### 3. Нуриддинов Самариддин Абдисалим, договор `00000141165`

Продажа `00000057938` от `2025-10-06 17:35:22`.

## Почему пайплайн не нашёл эти числа раньше

1. `_InfoRg3060._Fld3072` было названо `rg_paid_candidate` без подтверждения
   его бизнес-смысла отчётом 1С.
2. На основе этого предположения `payment_left` вычислялся как
   `_Fld3070 - _Fld3072`. Если `_Fld3072` является долгом, поля неизбежно
   переставляются.
3. Бухгалтерский регистр `_AccumRg3305` вообще не участвовал в формуле денег,
   хотя именно в нём находятся начисления, оплаты, распределение по продаже
   и корректировки.
4. SQL выбирал только один `TOP (1)` платёж. В основном он использовался для
   определения способа оплаты, а не для полного финансового баланса.
5. Суммы `_Document152_VT1083._Fld1090`, распределённые на конкретную
   продажу, не суммировались. Общий итог платёжного документа нельзя
   использовать вместо них из-за общих платежей на несколько продаж.
6. Многие записи были 50/50. Неверная трактовка поля оставалась незаметной,
   потому что оплачено и долг имели одинаковое значение.
7. Эти строки ранее были сознательно вынесены в problem3 как активные
   договоры с положительным `payment_left` без слова «рассрочка». На тот
   момент не было эталонного отчёта менеджера, подтверждающего семантику
   регистров.

## Отдельное временное расхождение в менеджерском файле

Для четырёх из десяти договоров поле `Оплачено` менеджерского XLSX больше
суммы, реально существующей в backup на `2026-06-30 23:27:03`:

| Договор | Разница |
| --- | ---: |
| `00000152426` | `10990` |
| `00000148035` | `5994` |
| `00000146660` | `7495` |
| `00000151875` | `2748` |

Сам XLSX был экспортирован `2026-07-21`, примерно через три недели после
завершения backup. Точная причина пока не доказана, потому что в XLSX нет
параметров запроса и текста отчёта 1С.

Наиболее вероятные объяснения:

- оплаты или вспомогательные операции были добавлены либо перепроведены в
  живой базе после создания backup;
- отчёт одновременно показывает задолженность на `30.06.2026`, но оборот
  «Оплачено» в другом временном диапазоне.

Это именно гипотезы. По backup доказано только следующее: указанных четырёх
дополнительных сумм на cutoff нет ни в платёжных документах, ни в
распределённых строках, ни в движениях регистра по соответствующим клиентам
и продажам.

## Итог

Причина основной массы расхождений найдена:

- `Продано` нужно брать на уровне строки продажи;
- `Задолженность` нужно считать как баланс `_AccumRg3305`;
- `Оплачено` нужно собирать из всех распределённых на конкретную продажу
  движений, а не из `_InfoRg3060._Fld3072` и не из одного платёжного документа;
- корректировки регистра обязательны;
- четыре значения `Оплачено` требуют более свежего backup или точных
  параметров отчёта 1С, поскольку в snapshot на `30.06.2026` их нет.
