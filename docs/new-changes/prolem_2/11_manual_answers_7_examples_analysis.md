## Что осталось открыть после этих ответов

### Открыто: no-payment active overlap

Не закрыто автоматическим правилом. Новые ответы показали смешанный слой:

- `4` из `7` примеров - лишние продажи, которые менеджер удалила;
- `3` из `7` - реальные/оплатные/future строки, которые надо переносить.

Следующее действие: либо ждать финальную базу после чистки менеджера, либо
дорабатывать matcher оплат/рассрочек и затем снова считать остаток.

### Почти закрыто: zero-direct

Правило понятно, но перед внедрением нужно аккуратно посчитать
`amount_of_payments`:

- `price` для full без refund - из `membership_sale_line_amount`;
- `paid` - не из одного `matched_payment_amount`, а из суммы связанных
  direct-платежей;
- `Неделя Фитнес` - оставить zero/blank payment type.

### Частично закрыто: payment_left / retail

Закрыто:

- named-рассрочки;
- retail-исключение.

Открыто:

- non-named `payment_left > 0`, потому что часть долгов может быть закрыта
  вспомогательной продажей/эмулятором.

## Приоритет дальнейшей работы

1. Сначала zero-direct, потому что ответы дают достаточно четкое правило и
   затрагивают активные full-строки.
2. Затем retail-exclude, потому что бизнес дал прямое правило, а активных строк
   retail нет.
3. Затем named/non-named `payment_left`: named оставить, non-named искать через
   вспомогательную продажу/эмулятор.
4. No-payment active overlap не трогать массово без новой базы/нового matcher-а,
   потому что 7 ответов показали высокий риск удалить реальные future/payment
   строки.
