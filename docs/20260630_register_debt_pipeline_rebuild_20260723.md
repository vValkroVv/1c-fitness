## Что изменено

Финансовые поля клиентского абонемента теперь рассчитываются внутри основного
SQL/Python-пайплайна, без подстановки значений из менеджерского XLSX.

Для каждой однозначно определённой продажи используются:

- цена абонемента из регистра сведений, с fallback на строку продажи;
- оплата конкретной продажи из распределённых строк
  `_Document152_VT1083._Fld1090`;
- начисление, оплата и независимый остаток долга из `_AccumRg3305` на cutoff;
- номер и время документа продажи для защиты от повторяющихся исторических
  номеров.

Регистр `_AccumRg3305` ведётся на уровне продажи. Поэтому его баланс
переносится в абонемент только тогда, когда в продаже ровно одна ненулевая
финансовая строка и она является целевым абонементом. Это предотвращает
размножение суммы на продажах с несколькими абонементами или дополнительными
товарными строками.

`amount_of_payments` и `payment_left` рассчитываются независимо. Это важно для
корректирующих движений: равенство `цена - оплачено = долг` в исходной 1С
выполняется не всегда.

## Почему старый расчёт пропускал долги

Предыдущая логика смотрела в основном на цену из `_InfoRg3070` и на документы
оплаты. Поле `_Fld3072` не является универсальной суммой оплаты: в спорных
случаях оно отражает остаток долга. Кроме того, сумма шапки платёжного
документа могла относиться сразу к нескольким продажам.

Финансовая истина отчёта 1С находится в движениях регистра
`_AccumRg3305`. После агрегации этих движений по ссылке продажи и точному
cutoff прежние problem1–3 перестали быть проблемными.

## Воспроизведение

Из папки `end-to-end-xlsx/`:

```shell
.venv/bin/python scripts/run_pipeline.py \
  --config config/pipeline_register_debts_20260630.yml \
  --server 127.0.0.1 \
  --port 11434 \
  --database FitnessRestored_20260630_macos
```

Пароль передаётся только через переменную `FITNESS_SQL_PASSWORD`. Конфиг
жёстко проверяет равенство `cutoff_at`, `backup_finish_at` и
`RESTORE HEADERONLY.BackupFinishDate`; любое несовпадение останавливает прогон.
