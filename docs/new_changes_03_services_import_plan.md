Сформировать новые XLSX для импорта услуг:

## Зафиксированные решения

- Услуги строятся для того же набора клиентов, что абонементы: только финальный
  `import_заявки`.
- Переносим действующие услуги для всех клиентов из финального `import_заявки`.
- Действующая услуга: срок действия не закончился или есть остаток
  количества/посещений.
- Если какой-то услуги из списка 51 нет среди действующих, добавляем до 5
  исторических примеров по клиентам из финального `import_заявки`.
- Если найдено меньше 5 исторических примеров, берем максимум доступного.
- Если по услуге нет продаж/примеров, указываем это в отчете и выводим
  пользователю.
- Все 51 позиции импортируются как услуги, включая доплаты, заморозки, утери,
  сертификаты и аренду.
- Для денежных/штрафных/административных услуг `duration` и `visits` оставлять
  пустыми.
- `count` = количество услуг.
- Для пакета 12 тренировок: `count=1`, `visits_left=остаток`.
- Для разовой услуги: `visits_left=1`.
- Для солярия использовать `visits` или найденное количество минут.
- Если услуга активируется первым посещением, но посещений не было,
  `activation_date` оставлять пустым.
- Если услуга бессрочная, `end_date` оставлять пустым.
- Продукты вроде `Пакет 12 (персональные тренировки)` идут и в импорт услуг, и
  могут продолжать участвовать в классификации воронок.
- Цена шаблона услуги = последняя фактическая цена продажи.
- Несколько product_ref с одинаковым названием объединяем в один шаблон.
- Финансовые поля услуг считаем по тем же правилам, что абонементы.
- `do_enter`, `first_visit_activation`, `archive`, `category`, `legal_entity`
  заполняем по инженерному усмотрению максимально релевантно.

## Что уже понятно по бизнес-логике

Из переписки:

- услуги переносим для тех же клиентов, которые загружаются через заявки;
- нужны только услуги из списка 51;
- переносим активные услуги;
- если по одной из 51 услуг нет активных экземпляров, добавляем хотя бы одну неактивную/историческую строку по любому клиенту, чтобы услуга появилась после импорта;
- для клиентской строки нужны ФИО, телефон, название услуги, даты продажи/активации/окончания, остаток посещений, цена, оплачено, остаток к оплате, тип оплаты, менеджер.

## Что уже видно по текущим staging-данным

В `output/part2_20260525_0800_final/staging/stg_products.csv` большинство названий из списка 51 находятся как продукты 1С.

При этом текущая staging-логика продаж/членств не является полноценным источником услуг:

- часть услуг имеет `observed_sale_rows=0`, хотя продукт есть в справочнике;
- часть услуг выглядит как персональные тренировки/пакеты;
- `Пакет 12 (персональные тренировки)` сейчас участвует в классификации воронок как условный `full_subscription`, если у клиента нет другого полноценного абонемента;
- поэтому для импорта услуг нужен отдельный источник и отдельная классификация, а не простое переиспользование текущего `stg_subscriptions_all`.

## Предлагаемая логика состава строк

Итоговое правило:

1. Берем итоговый список клиентов из финального импорта заявок после фильтров и дедупликации.
2. Ищем по ним активные услуги из списка 51.
3. В клиентский XLSX пишем одну строку на один экземпляр услуги клиента.
4. После этого проверяем покрытие всех 51 названий.
5. Если по названию нет активной строки, ищем до 5 исторических/неактивных
   продаж этой услуги только среди клиентов финального `import_заявки`.
6. Если по названию вообще нет продаж/экземпляров для выбранных клиентов,
   оставляем услугу только в шаблонах и фиксируем это в отчете.

## Валидация

Минимальные проверки:

- заголовки XLSX совпадают с шаблонами;
- все 51 услуги присутствуют в шаблонах;
- все `service_name` в клиентском файле входят в список 51;
- по каждой из 51 услуг есть либо клиентская строка, либо причина отсутствия клиентской строки в отчете;
- обязательные поля заполнены;
- все клиенты активных услуг входят в финальный импорт заявок, если это подтвержденное правило;
- для исторических fallback-строк отдельно помечается, почему они добавлены;
- суммы `price`, `amount_of_payment`, `payment_left` проходят базовые проверки;
- нет дублей по `service_id`;
- услуги, которые также похожи на абонементы, не ломают классификацию воронок.

## Риски

- Услуги могут храниться в других регистрах, не в текущем источнике членств.
- Для части услуг может не быть активных экземпляров у клиентов из финального импорта заявок.
- Для части услуг может не быть продаж вообще, только шаблон продукта.
- Остаток посещений может быть регистровым остатком, а не простым расчетом от количества продаж.
- Пакеты персональных тренировок могут пересекаться с текущими правилами определения `Действующих клиентов`.

## Оставшиеся технические проверки

1. Найти фактический источник услуг, остатков посещений, списаний, дат и оплат.
2. Проверить покрытие всех 51 услуг по выбранным клиентам.
3. Отдельно вывести услуги, по которым нет активных строк и нет 5 исторических
   примеров.
4. Проверить, что продукты, одновременно участвующие в воронках и услугах, не
   меняют уже подтвержденную классификацию воронок.
