# Источники 1С-отчетов по клиенту: подчиненность, операции, оплаты

Дата разбора: `2026-06-24`.

Срез импорта: `2026-05-25 08:00`.

Цель: понять, можем ли в SQL-бэкапе найти те же сущности, которые менеджер
видит в 1С-отчетах по клиенту:

1. `структура подчиненности`;
2. `история операций`;
3. `регистры оплат`.

Проверочные SQL/log:

```text
sql/74_client_report_like_sources_probe.sql
logs/new-changes/prolem_2/74_client_report_like_sources_probe.clean.txt

sql/75_client_report_sources_summary.sql
logs/new-changes/prolem_2/75_client_report_sources_summary.clean.txt
```

## Верхний вывод

Да, большую часть того, что менеджер видит отчетами в 1С, мы можем найти в
SQL. Но это не один готовый отчет, а несколько физических таблиц 1С:

| блок в 1С | можем найти? | SQL-источник | надежность для импорта |
|---|---|---|---|
| структура подчиненности | да | связи `Document163` -> `Document154` -> `Document152`, плюс `Document138`/`Document131` | высокая, можно строить audit/matcher |
| история операций | частично | `Document138` для бизнес-операций по членству; `DocumentJournal*` для клиентской ленты документов | высокая для операций изменения условий, низкая для полной истории правок |
| регистры оплат | да | `_AccumRg3305` как регистр движений долг/оплата по клиенту и продаже | высокая, нужно подключать к спорным payment matcher-ам |
| полная история изменений 1С | нет | `_DataHistory*` есть, но пустые | использовать нельзя |

## 1. Структура подчиненности

В SQL нет отдельной таблицы с готовым деревом "структура подчиненности". Но
дерево восстанавливается по ссылкам документов.

Основная карта:

| смысл | таблица | как связывать |
|---|---|---|
| членство/абонемент | `_Document163`, type ref `0x000000A3` | `Document163._IDRRef` |
| продажа членства | `_Document154`, type ref `0x0000009A` | через строки продажи |
| строка продажи, указывающая на членство | `_Document154_VT1137` | `_Fld1148_RTRef = 0x000000A3`, `_Fld1148_RRRef = Document163._IDRRef` |
| платежный документ | `_Document152`, type ref `0x00000098` | через строки платежа |
| строка платежа, указывающая на продажу/членство/операцию | `_Document152_VT1083` | `_Fld1087_RTRef/_Fld1087_RRRef` |
| операция по членству | `_Document138`, type ref `0x0000008A` | `_Fld763RRef = Document163._IDRRef` |
| возврат | `_Document131`, type ref `0x00000083` | `_Fld545_RRRef` или `_Fld547_RRRef` на продажу |

Примеры из текущих спорных кейсов:

| contract_id | что восстановилось в дереве |
|---|---|
| `00000149776` | `Document154 sale 00000025519` + `Document163 membership 00000149776`, платежа в дереве нет |
| `00000150179` | `Document154 sale 00000027876` + `Document163 membership 00000150179`, платежа в дереве нет |
| `00000150540` | `Document154 sale 00000029860` + `Document163 membership 00000150540`, платежа в дереве нет |
| `00000138477` | продажа + членство + операция `Заморозка абонемента 2 месяца` + direct payment |
| `00000145694` | продажа + членство + direct payment `00000003672` на `7 995` |

Вывод: "структуру подчиненности" можно строить программно. Это особенно важно
для `zero-direct`, где платеж есть в дереве, но цена в целевой строке членства
равна нулю.

## 2. История операций

Для бизнес-операций по членству найден надежный источник:

```text
dbo._Document138
```

Поля, которые уже подтверждены:

| поле | смысл |
|---|---|
| `_IDRRef` | ссылка операции |
| `_Number` | номер операции |
| `_Date_Time` | дата операции, с учетом 1С offset `-2000 years` |
| `_Posted` / `_Marked` | проведено / помечено на удаление |
| `_Fld763RRef` | ссылка на членство `Document163` |
| `_Fld764RRef -> _Reference72._Description` | тип операции/модификатор |
| `_Fld762RRef -> _Reference64` | старый/текущий клиент в операции |
| `_Fld767RRef -> _Reference64` | новый владелец/клиент, если операция меняет владельца |
| `_Fld773`, `_Fld771` | текстовые комментарии-кандидаты |
| `_Fld775` | числовой кандидат: сумма/дни, зависит от операции |

На проверочном наборе:

| contract_id | операция |
|---|---|
| `00000134419` | `6 месяцев в подарок`, дата `2025-04-20 13:21:38` |
| `00000138477` | `Заморозка абонемента 2 месяца`, дата `2025-08-01 14:24:30` |

Ограничение: это не полная "история правок". Таблицы 1С DataHistory есть, но
все пустые:

| таблица | rows |
|---|---:|
| `_DataHistoryAfterWriteQueue` | `0` |
| `_DataHistoryLatestVersions` | `0` |
| `_DataHistoryLatestVersions1` | `0` |
| `_DataHistoryLatestVersions2` | `0` |
| `_DataHistoryMetadata` | `0` |
| `_DataHistoryQueue0` | `0` |
| `_DataHistorySettings` | `0` |
| `_DataHistoryVersions` | `0` |

Значит:

- операции типа `Смена владельца`, `Смена владельца подарочной карты`,
  `Заморозка`, `6 месяцев в подарок` и похожие можно искать;
- кто вручную менял реквизит/статус/дату, если это не создало документ
  операции, из `_DataHistory*` восстановить нельзя.

## 3. Регистры оплат

Главный найденный источник:

```text
dbo._AccumRg3305
```

По проверенным строкам он выглядит как регистр движений долга/оплаты:

| поле | смысл |
|---|---|
| `_Period` | дата движения, с учетом 1С offset |
| `_RecorderTRef/_RecorderRRef` | документ-регистратор движения |
| `_RecordKind` | направление движения: в проверенных кейсах `1` = начисление/продажа, `0` = оплата/закрытие |
| `_Fld3307_RTRef/_Fld3307_RRRef` | клиент, для клиента `RTRef = 0x00000040` -> `_Reference64` |
| `_Fld3308_RTRef/_Fld3308_RRRef` | связанный документ, чаще всего продажа `Document154` |
| `_Fld3311` | сумма движения |
| `_Fld3312`, `_Fld9180` | дополнительные числовые поля, в проверенных платежных движениях обычно `0` |

Что это дает:

- `Document152` показывает платежный документ;
- `_Document152_VT1083` показывает, к какой продаже/документу платеж привязан;
- `_AccumRg3305` показывает, был ли долг по продаже реально закрыт движением
  оплаты, даже если прямой payment matcher не сработал.

На спорных no-payment строках:

| contract_id | целевая продажа | движение по целевой продаже в `_AccumRg3305` |
|---|---|---|
| `00000149776` | `00000025519`, `12 990` | есть только `record_kind=1` на `12 990`; закрывающего `record_kind=0` на эту продажу нет |
| `00000150179` | `00000027876`, `11 990` | есть только `record_kind=1` на `11 990`; закрывающего `record_kind=0` на эту продажу нет |
| `00000150540` | `00000029860`, `11 990` | есть только `record_kind=1` на `11 990`; закрывающего `record_kind=0` на эту продажу нет |
| `00000134419` | `00000025747`, `15 970` | есть только `record_kind=1` на `15 970`; потом у клиента есть другая sale/payment пара `00000034248`/`00000033584` на `10 900` |
| `00000142446` | `00000064417`, `10 990` | есть только `record_kind=1`; позже есть другая sale/payment пара `00000014685`/`00000015143` на `11 990` |
| `00000145694` | `00000003608`, `15 990` | есть sale `record_kind=1` на `15 990` и payment `record_kind=0` на `7 995`; остаток `7 995` требует поиска второй оплаты/эмулятора |

Поэтому текущий вывод по фразе менеджера "платеж есть":

- если смотреть строго подчиненность целевой продажи, платеж не находится;
- если смотреть весь регистр клиента вокруг даты продажи, другие оплаты/продажи
  есть, но они не закрывают целевую продажу напрямую;
- для автоматического исправления нужен отдельный matcher "оплата/продажа
  рядом у того же клиента", а не просто direct `Document152 -> Document154`.

## 4. Клиентский журнал документов

Дополнительный источник:

```text
dbo._DocumentJournal1621
```

Он дает клиентскую ленту документов:

| document_tref | найденный смысл |
|---|---|
| `0000009A` | `Document154`, продажа |
| `00000098` | `Document152`, платеж |
| `000000A3` | `Document163`, членство |
| `00000083` | `Document131`, возврат |

Для привязки к клиенту в этом журнале работает:

```text
_Fld1623_RTRef = 0x00000040
_Fld1623_RRRef = _Reference64._IDRRef
```

Ограничение: `Document138` с операциями изменения условий в основные журналы
`1607/1621/1627` не попал, поэтому операции по членству нужно брать напрямую
из `_Document138`, а журнал использовать только как клиентскую ленту продаж,
платежей, членств и возвратов.

## Практический вывод для открытых проблем

1. Для `zero-direct` активных full-строк можно опираться на структуру
   подчиненности и `_AccumRg3305`: там видно продажу, платеж и движение
   регистра. Это хороший источник для восстановления цены/оплаты.

2. Для no-payment cash активных строк direct payment не найден не потому, что
   мы не знали про `Document152`, а потому что у целевых продаж часто нет
   закрывающего движения в структуре/регистре. Следующий шаг - искать payment
   по клиенту вокруг даты и решать, какие "другие продажи" можно считать
   оплатой целевого членства.

3. Для non-named `payment_left > 0` регистр `_AccumRg3305` важнее текущего
   `matched_payment_amount`: он показывает, есть ли по продаже остаток долга и
   какие другие движения у клиента были рядом. На примере `00000145694`
   видно только половину оплаты (`7 995` из `15 990`) на целевую продажу;
   вторую половину надо искать через вспомогательную продажу/эмулятор.

4. Полную историю ручных изменений из 1С восстановить нельзя: `_DataHistory*`
   пустые. Если менеджер видит "историю операций" именно как бизнес-операции
   по членству, это `_Document138`; если как аудит изменения реквизитов, этого
   источника в бэкапе нет.
