## Исторический вердикт по прежней папке

## Прямое подтверждение в коде

На момент прежней сборки в рабочем SQL дата была зашита жёстко:

```sql
-- sql/31_build_membership_import_staging.sql
DECLARE @cutoff_at datetime2(0) = '2026-05-25 08:00:00';

-- sql/54_build_services_import_staging.sql
DECLARE @cutoff_at datetime2(0) = '2026-05-25 08:00:00';
```

Команды прежней июньской пересборки передали новую дату только в owner/funnel-этап.
В `scripts/31_build_membership_import_outputs.sh` и
`scripts/32_build_services_import_outputs.sh` нет параметра cutoff, который мог бы
переопределить жёсткую дату SQL.

В позднее собранном `end-to-end-xlsx/` SQL был сделан параметрическим,
но в прежней версии `end-to-end-xlsx/config/pipeline.yml` для обоих этапов было оставлено
`2026-05-25 08:00:00`, чтобы пакет повторил уже собранные эталонные XLSX.
То есть standalone-пакет воспроизводит эту же ошибку.

## Масштаб для абонементов

В июньском `stg_subscriptions_all.csv` между
`2026-05-25 08:00:00` и `2026-06-30 23:27:03` есть:

- `1481` потенциальная строка импорта абонемента всего;
- `1475` из них относятся к `65231` клиенту текущего source-union;
- это `1435` разных клиентов;
- из `1475` строк `1236` активны на 30 июня;
- это `1221` уникальный активный клиент.

Эти `1475` строк не могли попасть в текущий SQL абонементов из-за прямого
условия `sale_datetime <= @cutoff_at`.

Это минимально видимый по июньскому stage масштаб изменения.
После полной пересборки на 30 июня могут
также измениться расчёты оплат, остатков посещений, активности, филиала продажи
и состав трёх problem-файлов. Поэтому нельзя просто дописать `1475` строк в старый XLSX:
нужен полный SQL-прогон.

Точный масштаб пропущенных июньских услуг можно получить только повторным
запуском их SQL на нужном cutoff или отдельным count-запросом к восстановленной базе.

## Почему валидаторы пропустили ошибку

Валидаторы проверяли:

- схему и количество колонок;
- уникальность `contract_id`;
- обязательные поля;
- совпадение с промежуточными фактами;
- точные контрольные счётчики уже собранной поставки.

Они не сравнивали `cutoff_at` абонементов/услуг с датой основного прогона.
Поэтому `PASS` означал «XLSX верен майскому фактовому слою», а не
«все файлы полные на 30 июня».
