# Единый план финального переноса 1С → Fitbase, 20–21 сентября 2026

Этот документ — актуальная инструкция для финального запуска. Основа — принятая
июньская поставка `output/20260630_delivery_funnel_labels_20260820/` и уточнения
заказчика от 20 сентября. Исторические июньские команды переименования и
исправления дат услуг не являются командами финального сентябрьского запуска.

## 1. Согласованные правила

20 сентября заказчик ответил: «Вечер 20 делать как вечер 21». Для сегодняшнего
запуска используем **BackupFinishDate + 1 сутки с сохранением часов, минут и
секунд**. Например, `2026-09-20 22:17:05` → `2026-09-21 22:17:05`.
Если понадобится другое точное время, оно задаётся через `--effective-at`.
Момент `23:59:59` автоматически не подставляется.

Две даты имеют разный смысл:

```text
backup_finish_at = фактический RESTORE HEADERONLY.BackupFinishDate
cutoff_at = effective_at (согласованная дата и время актуальности)
cutoff_date = date(cutoff_at)
date_stamp = YYYYMMDD(cutoff_at)
```

Если явное время или смещение не заданы, сохранён прежний режим:
`cutoff_at = backup_finish_at`. Это уточнение пользователя от 20.09 заменяет
прежний безусловный запрет на отличающийся cutoff. Для клиентов, воронок, карт,
абонементов, услуг, шаблонов, problem-файлов и фото действует **один cutoff**.
Несовпадение дат отдельных слоёв останавливает сборку.

Срез означает пересчёт состояний по доступным данным backup. Даты продаж,
платежей, начала и окончания договоров и услуг не сдвигаются на сутки.
Операции, которых нет в backup, не добавляются. Имеющиеся в backup документы
с будущей датой отбираются по общему времени актуальности во всех слоях.
Время задаётся в локальном времени исходной SQL-базы, как в HEADERONLY;
скрытого преобразования в UTC нет.

Менеджеры — единый пул для всех передаваемых клиентов, независимо от клуба:

- Пеуна Анастасия Ивановна;
- Пилия Анастасия Артуровна;
- Ефремова Алена.

Выбор воспроизводим по ID клиента, одинаково в заявках, абонементах и услугах,
включая клиента с услугой, отсутствующего в файле заявок. Все три имени допустимы для любого клуба;
строго одинаковое количество клиентов у каждого менеджера не требуется.
Отчество Ефремовой не выдумывается: в уточнении заказчика его нет.

Фото — отдельный общий ZIP для действующих клиентов и реактивации из нового
backup. Ответ «Все верно» от 20.09 подтверждает: в архиве остаются только
валидные телефоны. Отсутствующий/невалидный телефон и отсутствующее фото
исключают фотографию из ZIP. Это правило не удаляет клиента из XLSX.
Состав и телефоны фото сверяются с реально передаваемым файлом заявок после
переклассификации и удаления дублей. Изображения сохраняются в настоящем JPEG;
для нескольких клиентов с одним телефоном сохраняется согласованный ранее
суффикс `__ID` и отчёт соответствия. Имена без суффикса — телефон клиента.

Сохраняются принятые исправления:


потребует ещё места. Скрипт проверяет размер из FILELISTONLY и свободное место
до восстановления. Текущая июньская база и `.bak` при репетиции сохранены.

## 4. Основной запуск

На текущем Mac используем место уже восстановленной июньской базы. Следующая
команда **заменит локальную SQL-копию** новым вечерним backup, сохранив сам
июньский `.bak`, принятую поставку и результаты репетиции. Имя SQL-базы при этом
останется техническим именем прежней копии; источником дат/данных будет новый
backup, проверенный по UUID и HEADERONLY.

```bash
python3 scripts/run_fitbase_migration.py \
  --backup-file data/Fitnes-20-09-26.bak \
  --backup-sql-path /backup/Fitnes-20-09-26.bak \
  --database FitnessRestored_20260630_macos \
  --run-name 20260920_final \
  --effective-offset-days 1 \
  --restore --replace-existing \
  --restore-host-dir mssql-macos/data
```

Режим замены включается только явным `--replace-existing`. До замены должны
пройти проверки нового backup; скрипт проверяет локальное подключение, историю
полного восстановления, отсутствие пользовательских SQL-сессий, соответствие
логических файлов и место под рост файлов + 2 GiB. Физические MDF/LDF
используются повторно. Прежняя история и пути сохраняются в аудите.
На текущей июньской базе этот режим сегодня **не выполнялся**; он проверен на
отдельной маленькой SQL-базе с изменившимся содержимым.

Если достаточно места для новой базы, вместо этих двух параметров указать
`--database FitnessRestored_20260920_macos --restore` без `--replace-existing`.
Этот вариант требует места под полные MDF/LDF рядом с существующими.
Для уже восстановленного именно
сентябрьского backup вместо `--restore --restore-host-dir ...` используется
`--use-existing` и убрать `--replace-existing`; UUID, время и исходное имя базы проверяются по последнему
восстановлению в `msdb`. Нельзя направить сентябрьскую команду на июньскую базу
и получить успешный preflight.

Для точного времени заменить `--effective-offset-days 1` на, например:

```text
--effective-at "2026-09-21 22:17:05"
```

Варианты времени взаимоисключающие. `--prepare-only` выполняет только
подготовку и проверки. Без `--restore`/`--use-existing` он не утверждает, что
база уже готова. Полный запуск всегда требует одного из этих двух режимов.

Подготовка сохраняет в `end-to-end-xlsx/work/prepared/<run-name>/`:

- `backup_metadata.json`: SHA-256, размер, HEADERONLY, FILELISTONLY, VERIFYONLY,
  реальное время backup, выбранное время актуальности и история восстановления;
- `pipeline.yml`: конфигурация для этого backup;
- `expected.yml`: принятые структура/филиалы/инварианты без июньских счётчиков.

Далее выполняются: preflight → SQL клиентов → CSV и переклассификация →
заявки/карты → абонементы → услуги → problem-файлы → сборка поставки → проверки
XLSX → фото → проверка архива → хеши поставки → `READY.txt`.

## 5. Проверка перед передачей

Проверяем все контрольные материалы текущего запуска:

- `reports/structural_validation.md`: состав файлов, структура, уникальность
  договоров, разделение problem/чистой поставки, допустимые филиалы;
- проверки сборщиков заявок, абонементов и услуг в
  `end-to-end-xlsx/work/<run-name>/`: сверка с актуальным staging, менеджеры,
  телефоны, суммы и даты по действующим правилам;
- `reports/photos.json`: PASS, единый cutoff, оба сегмента, исключения,
  количество JPEG, CRC и хеши фотографий;
- `_reports/manifest.csv`, `_reports/excluded_clients.csv` и отчёт общих телефонов
  внутри ZIP: соответствие изображения клиенту и его передаваемому телефону;
- `reports/delivery_manifest.json`: реальные метаданные backup, время
  актуальности, SHA-256 всех передаваемых XLSX и ZIP;
- `READY.txt` создаётся последним после всех проверок. При возобновлении
  прежний маркер снимается, а изменившиеся после проверки файлы не получают PASS.

Отдельно просматриваем распределение менеджеров/воронок и причины исключения
фото. Проверяем несколько клиентов с истечением абонемента 20/21 сентября,
договорами/услугами на границе даты и несколькими телефонами. Старые июньские
имена файлов, количества и контрольный менеджерский XLSX автоматически не
подключаются к сентябрьскому запуску.

## 6. Ошибка и возобновление

Логи: `end-to-end-xlsx/logs/<run-name>/`; состояние:
`end-to-end-xlsx/work/<run-name>/status.json`.
Используем последний ошибочный этап из этого файла, например:

```bash
python3 scripts/run_fitbase_migration.py \
  --resume-config end-to-end-xlsx/work/prepared/20260920_final/pipeline.yml \
  --start-at photos
```

Возобновление допускается только при неизменной конфигурации, времени,
менеджерах, классификации, филиалах и контрольном manifest и при выполненных
предыдущих этапах. После изменения бизнес-параметров делаем **новый run-name**
и полный прогон. Общий SQL staging находится в одной базе; два запуска на одной
восстановленной базе одновременно не выполняем.
