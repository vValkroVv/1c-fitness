# Канонизация шаблонов абонементов

Файл `membership_template_canonicalization.csv` — обязательный проверяемый
справочник для названий, у которых в staging одновременно встречается больше
одного варианта `price / duration / visits / freeze / branches_access`.

## Контракт сборки

- один вариант названия строится автоматически;
- два и более варианта без строки в CSV останавливают сборку;
- по умолчанию настроенный вариант обязан реально встречаться в текущем staging;
- `source_contract_id` фиксирует договор, по которому принято решение, и на
  проверенной базе должен соответствовать настроенному варианту;
- если договор-источник больше не попал в клиентскую выборку нового backup, но
  сам настроенный вариант по-прежнему присутствует, сборка продолжается и пишет
  это в audit-счётчик;
- прежнее исключение для изменения только цены после пересчёта финансов
  сохраняет цену шаблона из CSV и актуальную цену индивидуального договора;
- `allow_historical_variant=1` разрешает только для указанного названия сохранить
  принятый исторический шаблон, если вариант исчез из staging или параметры
  договора-источника изменились, например из-за расходования заморозки или
  индивидуального изменения срока;
- применение исторического исключения обязательно фиксируется в счётчике и
  uncertainty `configured_historical_template_variant_preserved`: настроенные
  параметры, все текущие варианты, ID и текущие варианты договора-источника,
  основание решения и статус проверки;
- исключение изменяет только выбор шаблона: индивидуальные договоры сохраняют
  актуальные суммы, сроки, заморозку и даты из текущего backup;
- порядок строк и дата последней продажи никогда не выбирают шаблон;
- лишние строки конфига для отсутствующих в конкретном backup названий допустимы.

Таким образом, новый backup не может молча поменять существующий шаблон, а новый
конфликт требует явного решения в git.

## Поля

| Поле | Назначение |
| --- | --- |
| `canonical_name` | Отображаемое имя и ключ после нормализации регистра/пробелов |
| `branches_access` | `Все` или `Продажа` |
| `price` | Каноническая стоимость шаблона; ноль является значением, не пропуском |
| `duration` | Каноническая продолжительность в месяцах |
| `visits` | Лимит посещений либо пусто для безлимитного продукта |
| `freeze` | Дни заморозки либо пусто |
| `source_contract_id` | Контрольный договор для воспроизводимости решения |
| `decision_basis` | Основание выбора |
| `review_status` | Статус бизнес-проверки |
| `note` | Пояснение и оставшиеся ограничения |
| `allow_historical_variant` | Необязательное явное разрешение сохранить принятый исторический вариант: пусто или `0` — выключено, `1` — включено; остальные значения вызывают ошибку |

Без этого столбца действует прежняя строгая проверка. Разрешение не выбирает
параметры по цене или дате, не применяется к другим названиям и не создаёт
шаблон, если его название отсутствует в текущей выборке. Если разрешение задано,
но настроенный вариант и договор-источник проходят прежние проверки,
историческое исключение не считается применённым.

  заменяет окончательное решение менеджера по цене, сроку и заморозке.

## Как изменить решение

1. Найти все варианты названия в `membership_import_uncertainties.csv` и staging.
2. Подтвердить один вариант по данным 1С/решению бизнеса. Для сохранения
   исторического шаблона сверить все его параметры с принятой поставкой,
   указать источник подтверждения в `decision_basis` и `note` и только затем
   установить `allow_historical_variant=1` для этого названия.
3. Обновить поля CSV, `source_contract_id`, `decision_basis`, `review_status` и
   `note` одним коммитом.
4. Запустить unit-тесты и полную membership-сборку.
5. Убедиться, что configured variant найден либо историческое исключение явно
   отражено в audit и uncertainties, а новый XLSX прошёл валидацию.
