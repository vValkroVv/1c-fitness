## Зафиксированные решения

- Клиенты только из финального `import_заявки`; клиенты, удаленные фильтрами или
  phone-dedup, не попадают.
- Менеджер тот же, что в финальном `import_заявки`.
- Переносим все исторические абонементы выбранных клиентов, включая закрытые,
  пробные, гостевые, недельные, подарочные и короткие.
- Будущие/еще не активированные абонементы включаем, если они проданы до cutoff.
- Непроведенные, отмененные и возвращенные продажи исключаем.
- `create_date` = дата заведения клиента в систему, как в текущих заявках.
- `payment_date` = дата оплаты текущего абонемента.
- `activation_date` = фактическая дата активации.
- `end_date` = фактическая дата окончания.
- Если даты нет, вычисляем и фиксируем пометку в доп. отчете.
- `duration` = длительность шаблона.
- `duration_type` всегда `месяц`.
- Для `12+3`, подарочных месяцев и продлений пишем фактическую длительность,
  например 15 месяцев.
- Для недельных абонементов пишем `0` месяцев.
- `freeze`, `guests`, `visits_left` считаются на cutoff/момент backup.
- Для безлимитных `visits_left` оставляем пустым.
- Для субаренды нужен реальный остаток посещений.
- `amount_of_payments` = сколько уже оплачено.
- `payment_left` = весь неоплаченный остаток, включая будущие платежи по
  рассрочке.
- Типы оплаты: `наличные`, `безналичные`, `сбп`.
- `Доступ в филиалах`: `Все` для мультикарт, `Продажа` для остальных.
- Шаблоны абонементов строим по абонементам, которые относятся к клиентам из
  финального `import_заявки`.
- `contract_id` выбрать по смыслу после SQL-discovery; для переоформленного
  членства использовать новый идентификатор членства/новой сущности, если он
  есть.

## Что уже понятно по бизнес-логике

Из переписки:

- выгружаем абонементы для клиентов, которые уже попали в текущую выгрузку заявок/воронок;
- если у клиента было 10 абонементов, нужно перенести все 10;
- карточные/клиентские данные повторяются в каждой строке абонемента;
- перед этой задачей нужно исправить смену владельца;
- `guests` можно оставлять пустым, потому что гостевые визиты в Fitbase не используются;
- `visits_left` нужно заполнять только для абонементов с ограничением посещений, особенно для субаренды;
- менеджер должен быть тем же, что в текущем импорте заявок;
- типы оплаты в 1С встречаются как минимум: `наличные`, `безналичные`, `СБПР`;
- по рассрочке нужны корректные `amount_of_payments`, `payment_left`, `type_of_payment`.

Из DOCX по рассрочке:

- есть активное членство с просроченным платежом;
- есть закрытое членство с долгом;
- есть активное членство в рассрочке без просрочки, но с будущими платежами;
- в 1С есть график рассрочки, платежные документы, движения по регистрам и поле долга клиента;
- нельзя просто считать долг как `price - сумма платежей` без проверки источников в базе.

## Предлагаемая логика состава строк

Итоговое правило:

1. Берем итоговый список клиентов из финального импорта заявок после всех фильтров и дедупликации.
2. Для каждого клиента берем все его абонементы из 1С с учетом смен владельца.
3. В клиентском XLSX одна строка равна одному абонементу клиента.
4. Если абонемент был передан новому владельцу, строка должна быть у нового владельца.
5. Если у клиента нет абонементов, строка в этом файле не создается.

## Валидация

Минимальные проверки:

- заголовки XLSX совпадают с шаблонами;
- обязательные поля заполнены;
- все строки клиентских абонементов ссылаются на клиента из финального импорта заявок;
- все `contract_name` присутствуют в файле шаблонов;
- нет дублей по `contract_id` у разных клиентов, кроме случаев, явно разрешенных сменой владельца;
- переданные членства находятся у нового владельца;
- рассрочки из примеров проверены вручную по `amount_of_payments`, `payment_left`, `type_of_payment`;
- даты не выходят за ожидаемые границы;
- итоговые суммы и количество строк задокументированы.

## Риски

- Финансовые поля могут храниться в разных местах для обычной продажи, рассрочки, возврата, переноса и доплаты.
- Некоторые абонементы могут быть без даты активации или без даты окончания.
- Длительность в месяцах нельзя всегда надежно получить из количества дней: 365, 395, 455 дней и подарочные месяцы требуют отдельного правила.
- Значения `duration_type`, `first_visit_activation`, `archive`, `branches_access` должны совпасть с тем, что реально принимает Fitbase.
- Если в клиентский файл попадут все исторические абонементы, объем файла может быть значительно больше текущей выгрузки заявок.

## Оставшиеся технические проверки

1. Найти источники `contract_id`, оплат, долга, типа оплаты, заморозки и
   остатков посещений.
2. Проверить рассрочки по трем DOCX-примерам.
3. Проверить, что `duration_type=месяц` и пустые `visits_left` для безлимитных
   проходят локальную валидацию шаблона.
