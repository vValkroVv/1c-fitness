# Повторная проверка дублей и исключений фотографий

Проверен именно фотоархив компактного комплекта для заказчика:
`output/20260921_fitbase_for_customer/fitbase_client_photos_20260921.zip`.
Файлы поставки при проверке не менялись.

## Готовый архив

- 35 422 записи manifest, 35 422 уникальных client_id.
- 35 422 уникальных назначенных телефона и имени JPEG.
- Повторяющихся телефонов/имён нет; суффиксов `__ID` нет.
- `phone_filename_exceptions.csv` содержит только заголовок.

Правило экспортёра сохраняет фотографии клиентов с общим валидным телефоном:
сначала использует доступный альтернативный номер клиента, затем суффикс
`телефон__ID.jpg`, если без него возникает совпадение. Само совпадение
телефона не служит причиной удаления фотографии на этом этапе.

## Реальный состав исключений

| Причина | Количество |
| --- | ---: |
| Отсутствуют цифры телефонного номера, включая заглушки | 485 |
| Телефон содержит цифры, но не проходит нормализацию | 157 |
| Не найдено подходящее фото | 4 444 |
| Кандидат с фото отсутствует в конечном файле заявок | 6 278 |

Для передаваемых 40 508 клиентов: 35 422 фотографии и 5 086 исключений
по телефону или наличию изображения. Ещё 6 278 фото-кандидатов исключены
условием принадлежности конечному XLSX. Следовательно, описание
«исключили только невалидные номера» не отражает полный отбор.

## Дедупликация клиентов до отбора фото

При подготовке XLSX по прежним правилам исключены 2 388 клиентских записей
с общими телефонами: 2 017 новых заявок, 303 реактивации, 68 действующих.
В фотоархив допускаются только ID из конечных заявок после этого отбора.

Сопоставление ID из отчёта дедупликации с `not_in_delivered_workbook` внутри
фотоархива дало 346 совпадений:

- 180 клиентов реактивации;
- 64 действующих клиента;
- 102 новых заявки, которые не относятся к двум передаваемым фото-сегментам.

Таким образом, для 244 действующих/реактивации был найден фото-кандидат
в источнике, но клиент исключён из конечных заявок по общему телефону.
На этапе фотографий это стало причиной `not_in_delivered_workbook`.
Декодирование этих исключённых изображений не проводилось, поэтому проверка
не утверждает, что все такие BLOB пригодны для JPEG-архива.

Это соответствует текущему плану: состав фото сверяется с фактически
передаваемыми клиентами после удаления дублей. Правило о суффиксе `__ID`
сработало бы для общего номера нескольких клиентов, оставшихся в конечном
XLSX. В этой поставке таких случаев не оказалось.
