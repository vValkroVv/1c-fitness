# Дополнительная поставка 371 исключённого клиента

Запрос пользователя от 22.09.2026: выгрузить ровно 68 действующих клиентов
и 303 клиента реактивации, исключённых по телефону в поставке 21 сентября;
сохранить состав полной выгрузки, кроме файла пластиковых карт.

Папка: `output/20260921_phone_dedup_supplement_371/`.
Технические материалы: `end-to-end-xlsx/work/20260921_phone_dedup_supplement_371/`.

## Данные и состав

Отбор выполнен по уникальным `client_id` из
`end-to-end-xlsx/work/20260921_final_v2/owner/reports/phone_deduplication_removed_clients.csv`.
Внутренние воронки: `Действующие клиенты` — 68, `Реактивация` — 303.
Состав сверяется с `owner/staging/final_funnel_clients.csv` того же прогона.
Повторная дедупликация не применяется; исходные телефоны сохранены полностью.

В папке также находится README с особенностями импорта. Файл пластиковых карт

дополнительной выгрузки. Параметры шаблонов сохранены из принятой полной поставки.

## Срез и воспроизведение бизнес-правил

`backup_finish_at = 2026-09-20 20:12:12`,
`cutoff_at = 2026-09-21 20:12:12` для всех слоёв.
Клиенты, менеджеры, карты, абонементы и услуги восстановлены из сохранённых CSV
и TSV прогона `20260921_final_v2`, а не из текущего SQL staging за 22 сентября.
Во всех строках фактов проверен cutoff; ID и имена сверены с отчётом исключений.

Значения абонементов рассчитаны существующим `19_build_membership_import_xlsx.py`.
Цены, платежи, долги, даты и переоформления используют прежние правила.
Канонические параметры шаблонов взяты из принятого XLSX 21 сентября,
чтобы уменьшенная выборка не выбирала другой вариант цены или срока.

Услуги рассчитаны существующим `23_build_services_import_xlsx.py` на совокупности
клиентов основной поставки и этих 371 ID; затем оставлены только строки 371 ID.
Так сохраняется общий выбор действующих услуг и исторических примеров:
5 строк `active` и 5 строк `historical_fallback`. Отбор по уменьшенной выборке
не запускает новые исторические примеры для каждого вида услуг.

Все 68 действующих клиентов имеют строки абонементов. Четыре клиента
реактивации присутствуют в заявках, но не имеют строк в сохранённом
`membership_import_facts.tsv`: 000027427, 000036594, 000065047, 000065636.
Их пять исторических записей в `stg_subscriptions_all.csv` относятся к АКВА
и подарочному сертификату, исключённым прежним отбором продуктов. Правило
не менялось, отсутствующие импортные строки не создавались искусственно.
Харин 000025114 включён с девятью абонементами; договор 00000149164 сохранён
с окончанием 07.08.2027, ценой и оплатой 11 990, долгом 0.

## Фото и общие телефоны

Для фото выполняются только SELECT исходных BLOB в восстановленном сентябрьском
backup. UUID последнего восстановления сверён с
`8e76ec9f-004f-4291-9842-92017c8e9f53`, время backup — с 20.09.2026 20:12:12.
Фото отбираются по историческому списку 371 ID без обращения к staging другого
среза. Существующие процедуры декодирования, упаковки и проверки JPEG сохранены.

Найдено 244 фото: 64 действующих, 180 реактивации. Для остальных 127 отсутствует
подходящий фотофайл. JPEG проверены декодированием, CRC, размером и SHA-256.

Имена учитывают номера **всех** клиентов основной и дополнительной поставки:
50 фото — уникальный первый номер, 34 — уникальный альтернативный номер,
160 — общий номер с суффиксом `__client_id`. Это предотвращает как совпадение
имён с уже переданным архивом, так и неоднозначное назначение общего телефона
для автоматического импорта. Для 160 файлов требуется сопоставление по ID;
эта особенность указана в README и manifest внутри ZIP.

## Технический журнал и проверки

Скрипт `scripts/build_20260921_phone_dedup_supplement.py`:
`prepare` → авторинг XLSX → `photos` → `finalize`.
Авторинг: `scripts/write_20260921_phone_dedup_supplement.mjs` с Artifact Tool
из установленного runtime; `node_modules` в рабочей папке ссылается на runtime.
Для повторного сохранения только созданных в этой задаче XLSX поддержан
`--replace-generated`; прежняя поставка не перезаписывается.

Визуально просмотрены все пять листов. Показ числовых строк в PNG Artifact Tool
не сохраняет ведущие нули, поэтому отдельно проверены значения и типы ячеек
в реальных XLSX: ID и номера договоров остаются строками с ведущими нулями.
После проверки вида чисел формат целых/дробных показателей заменён на General,
чтобы не показывать завершающую десятичную точку; данные не менялись.

Финальная проверка повторно читает все значения пяти XLSX и сверяет с подготовленными
строками; проверяет 371 ID, 68/303, отсутствие посторонних клиентов, согласованность
ФИО/телефонов/менеджеров, отсутствие файлов карт и problem4, а также отсутствие
совпадений имён JPEG с основной поставкой. Хеши всех исходных файлов поставки
и материалов прогона сверяются с хешами до сборки.

Результат записывается в `validation.json`, `delivery_manifest.json` и `READY.txt`
в технической рабочей папке. Контрольные JSON, CSV и PNG не попадают в папку
заказчика. Исходная поставка, pipeline, конфигурации и SQL staging не изменялись.
Загрузка данных в Fitbase не выполнялась.
