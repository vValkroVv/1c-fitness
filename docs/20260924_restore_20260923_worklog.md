# Подготовка восстановления backup от 23.09.2026

## Источник и среда

- Backup: `data/Fitnes-23-09-26.fast.bak`, 13 629 527 552 байта.
- SHA-256: `3cdb039181a9a5d94c99d921843dd1de1b974deb113b32d27b846183d9a8872c`.
- `RESTORE HEADERONLY.BackupFinishDate`: 2026-09-23 23:36:39.
- `HEADERONLY`, `FILELISTONLY`, `VERIFYONLY` пройдены до этого запуска.
- SQL-контейнер: `mssql-fitness-2022`, SQL Server 2022, backup смонтирован в `/backup`.

## Первичная проверка

До остановки обнаружена только одна пользовательская SQL-база:
`FitnessRestored_20260630_macos`, фактически из backup от 20 сентября.
История `msdb` подтверждает `BackupFinishDate` 2026-09-20 20:12:12.
Июньская база присутствует в истории восстановления, но сейчас не зарегистрирована
в `sys.databases` и её MDF/LDF отсутствуют в `mssql-macos/data`.

Пользователь просил временно остановить сентябрьскую базу и очистить память Docker.
База переведена в `OFFLINE` без удаления файлов. Контейнер SQL перезапущен;
после запуска SQL отвечает, база сохранила `OFFLINE`. Потребление RAM контейнера
снизилось примерно с 1,8 до 1,1 GiB. Контейнер PostgreSQL другого проекта
не затрагивался. В Docker build cache — 0 байт; глобальная очистка других
контейнеров и томов для освобождения RAM не требуется.

Для нового восстановления в отдельную базу по `FILELISTONLY` было нужно
80 404 807 680 + 3 699 376 128 байт файлов MDF/LDF и резерв 2 GiB,
всего 86 251 667 456 байт. После перезапуска доступно примерно
84 225 527 808 байт; дефицит — около 1,89 GiB.

## Освобождение места

Пользователь уточнил: восстановленную SQL-копию от 20 сентября удалить
полностью, оставить только исходный backup. Перед удалением SHA-256
`data/Fitnes-20-09-26.fast.bak` повторно проверен:
`a65f21760209e60ac3b2ffc49a15a9a308e02dd75ffeb5829c342c9d98170f52`.

`DROP DATABASE` удалил регистрацию базы, но оставил физические MDF/LDF,
поскольку база была `OFFLINE`. После проверки отсутствия зарегистрированных
файлов удалены ровно
`FitnessRestored_20260630_macos.mdf` и
`FitnessRestored_20260630_macos_log.ldf`.
Виртуальная машина Docker Desktop продолжала держать удалённые файлы открытыми;
остановка одного SQL-контейнера этого не изменила. После `docker desktop restart`
дескрипторы закрылись, свободное место выросло до ~158 GiB. PostgreSQL другого
проекта автоматически вернулся в состояние `healthy`. SQL-контейнер запущен
вновь. Оба файла `.bak` в `data/` сохранены.

## Восстановление нового backup

Целевая база: `FitnessRestored_20260923_macos`. Первый запуск
`scripts/run_fitbase_migration.py --restore --prepare-only` повторно успешно
проверил SHA-256, `HEADERONLY`, `FILELISTONLY` и `VERIFYONLY`, но клиентское
TDS-соединение оборвалось во время `RESTORE`. В SQL база осталась `RESTORING`,
активного запроса восстановления уже не было, MDF был создан, LDF ещё не был
создан. Ожидающий клиент остановлен; его аудит помечен `INTERRUPTED`.

Восстановление той же незавершённой базы повторено непосредственно через
`sqlcmd` внутри контейнера с теми же `MOVE`, `REPLACE` и `RECOVERY`.
Команда завершилась с кодом 0: 7 321 926 страниц за 81,300 секунды.
База обновлена SQL Server с версии 852 до 957 и открылась в `ONLINE`,
`MULTI_USER`, compatibility level 130.

Новая подготовка `20260923_restore_verified` через локальный SQL-мост
`127.0.0.1:11435` завершилась `PASS`. Её аудит сверил последнюю запись
восстановления `msdb` с исходным backup:

- исходная база `Fitness`, полная копия, позиция 1;
- `BackupFinishDate`: **2026-09-23 23:36:39**;
- `BackupSetGUID`: `98038663-5828-4efe-80e4-327dbff24e3e`;
- latest `restore_history_id`: 2002, `recovery = true`.

По умолчанию подготовленная конфигурация использует единый срез,
равный фактическому `BackupFinishDate`; дату для будущей поставки XLSX
здесь отдельно не выбирали. SQL-мост после проверки остановлен.
