- Backup: `data/Fitnes-30-06-26.bak`

## Требуемое бизнес-изменение

В `fitbase_active_clients_import_zayavki_20260630_all_funnels.xlsx` заменены
ровно две финальные подписи:

```text
Реактивация(годовые абонементы) -> Реактивация
Все закрытые абонементы         -> Закрытые годовые абонементы
```

Состав клиентов, порядок строк, менеджеры, филиалы, телефоны, даты и все
остальные значения не менялись.

## Изменение алгоритма

Отображение внутренней воронки `Реактивация` изменено в обоих рабочих
экземплярах `scripts/17_build_part2_combined_xlsx.py`. Поэтому любой будущий
прогон с режимом `customer_20260520_single_stage` сохраняет новую пару
автоматически, независимо от даты backup.

В обоих `scripts/18_validate_combined_single_stage_outputs.py` новая пара
добавлена в обязательный контракт финального XLSX, а историческая пара больше
не разрешена.

Для текущей immutable-поставки добавлены:

- `end-to-end-xlsx/scripts/run_funnel_label_rename_20260630.sh`;
- `end-to-end-xlsx/scripts/build_funnel_label_delivery.py`;
- `end-to-end-xlsx/tests/test_build_funnel_label_delivery.py`.

Таргетированный сборщик завершает работу с ошибкой, если меняется любая другая
ячейка, стиль, структура листа, OOXML-компонент или любой другой XLSX.

## Воспроизведение

Из `end-to-end-xlsx/`:

```shell
scripts/run_funnel_label_rename_20260630.sh
```

Команда берёт принятый owner-stage из `work/20260630_register_debts/owner`,
пересобирает заявки штатным алгоритмом, запускает owner-валидатор, создаёт
новую immutable-поставку из последней поставки с исправленными датами услуг и
проверяет все XLSX.

SQL для этой таргетированной операции не требуется: cutoff-aware стейджинг уже
был принят и не меняется. При полном прогоне из нового backup обновлённая пара
подписей применяется основным `run_pipeline.py` через изменённый сборщик.
