# Почему в Fitbase остались 716 заявок без связи с клиентом

Срез исходной поставки: **21.09.2026 20:12:12**. Фактически загруженный архив: `20260921_fitbase_for_customer.zip`. Живой остаток повторно собран в Chrome 22.09.2026, **20:53–21:03 МСК**; три примера проверены в реестре клиентов в **21:06 МСК**. В Fitbase ничего не изменялось.

## 1. Ответ на основной вопрос

**Заявки появились из клиентской истории 1С, а не потому, что эти люди заново оставили заявку.** Наш пайплайн создаёт для бывших клиентов записи в воронке реактивации. Для этого достаточно обнаружить ранее приобретённый продукт, учитываемый как абонемент, при отсутствии действующего абонемента на дату среза.

При этом ветка подготовки заявок и ветка подготовки абонементов использовали разные версии классификации продуктов:

- Заявки читали результат переклассификации: АКВА, сертификаты и некоторые пакеты тренировок уже считались абонементами.
- SQL абонементов читал исходную классификацию: эти же продукты оставались `unknown_review_required` и не проходили фильтр разрешённых классов.
- Поэтому клиент присутствовал в заявках, а его настоящая договорная история не попадала в импортный XLSX абонементов.
- По сообщению исполнителя Fitbase, карточки клиентов создавали только из файла абонементов. Клиенты, присутствующие лишь в заявках, этим способом создания карточек не охватывались.

**Завершённый срок сам по себе не был причиной исключения из файла абонементов. Непосредственная причина — фильтр исходного класса продукта.** Отдельно, в файле услуг, исторические пакеты действительно отбирались по другому правилу, описанному в примере Митюгина.

Условное представление цепочки:

```text
Реальная история клиента в 1С
  ├─ исправленная классификация → бывший клиент → заявка «Реактивация»
  └─ исходная классификация → unknown_review_required → нет строки абонемента
                                                        ↓
                               создание карточек только по абонементам
                                                        ↓
                                     заявка остаётся без связи с карточкой
```

Подпись этапа **«Закрытые годовые абонементы»** — принятая общая подпись в файле заявок. Она не означает, что каждый исходный продукт был годовым: в этой группе есть АКВА на 4 посещения и месячные сертификаты.

### Почему он попал в реактивацию

Для «Пакета 12» задано правило: считать основным абонементом, если у клиента нет другого основного абонемента. У Митюгина таких других абонементов нет. Два пакета признаны завершёнными основными абонементами, действующих — ноль. Поэтому появилась строка **26393** файла заявок: реактивация, дата **23.01.2020**, менеджер **Пеуна Анастасия Ивановна**, Гоголевский.

### Почему нет ни в абонементах, ни в услугах

**Абонементы:** исходный класс всех восьми записей — `unknown_review_required`. Ни одна не прошла SQL-фильтр. В подготовленных фактах абонементов — **0**, в переданном XLSX — **0**.

**Услуги:** все восемь продаж реально найдены в `services_import_facts.tsv`. У каждой:

- `rg3336_signed_balance = 0` — остаток посещений нулевой;
- `is_active_by_date = 0`;
- `is_active_on_cutoff = 0`.

Сборщик услуг выбирает активные записи. Для «Пакета 12» в общей поставке есть **262 активные строки других клиентов**, для «Пакета 8» — **78**. Поэтому исторические неактивные записи Митюгина не выбираются. Режим пяти исторических примеров включается только при полном отсутствии активных строк данного вида услуги, чего здесь нет.

Таким образом, **два разных отбора независимо убрали его историю из обоих импортных файлов**: классификация — из абонементов, отсутствие активности и остатка — из услуг.

## 7. Почему было 717, а теперь 716; опасные привязки

Точное соотношение:

```text
717 исходных клиентов без строк абонементов
− 2 заявки, теперь показывающие ссылки на другие клиентские карточки
+ 1 дополнительная заявка Цыбульник Татьяны вне исходного файла
= 716 текущих непривязанных заявок
```

## 8. Что уже известно и что необходимо решать отдельно

**Установлено:** клиенты и договорная история в 1С были; ветка заявок использовала эту историю; ветка абонементов отфильтровала её до формирования XLSX. Это объясняет 715 исходных заявок. У дополнительной Татьяны есть ещё исключение самой клиентки по общему телефону.

В [аудите 21 сентября](20260921_membership_coverage_audit.md) зафиксировано решение сохранить прежние правила импорта и передать исключённую историю контрольным CSV. Это объясняет, почему фильтр не меняли. Но решение о составе истории **не обеспечивает создание карточек** клиентов, если принимающая сторона строит реестр исключительно по абонементам. В [компактном архиве](20260921_customer_files_only.md), который фактически загрузили, контрольного CSV вообще не было; сам CSV не являлся импортом абонементов.

Есть два разных предмета исправления:

1. **Клиентские карточки и связи.** Клиенты файла заявок должны иметь самостоятельный путь создания карточек, даже когда импортируемых договоров нет. Сопоставление требует исходного ID и проверки личности; общей цифры 7 или семейного телефона недостаточно.
2. **Исторические покупки.** Если требуется полная договорная история, нужно отдельно пересмотреть состав импорта и привести классификацию ветки абонементов к согласованным правилам. Для пакетов тренировок дополнительно решить, передаётся ли вся завершённая история услуг. Создание карточки само по себе не возвращает 18 договоров Яцковец или восемь покупок Митюгина.

В этой проверке правила, поставка и Fitbase не изменялись. Исправление связей двух спорных случаев также не выполнялось.

## 10. Есть ли эти продукты в шаблонах

По дополнительному вопросу заказчика непосредственно прочитан XML обоих XLSX шаблонов в фактически переданной папке `output/20260921_fitbase_for_customer/`. Результат сопоставлен с SQLite исходников и сохранёнными каталогами Fitbase (436 ID шаблонов абонементов и 177 ID шаблонов услуг, включая архивные). Проверен также состав исправленных файлов с простым числовым форматом в `output/20260921_fitbase_templates_plain_numbers/`: названия в них те же.

| Обсуждаемый продукт | В переданных шаблонах абонементов | В переданных шаблонах услуг |
| --- | --- | --- |
| АКВА на 4, 8, 18, 36, 40 и другие количества посещений из этой группы | Нет | Нет |
| Подарочный сертификат 1 месяц безлимитного фитнеса | Нет | Нет |
| Пакет 12 (персональные тренировки) | Нет | Да, ячейка A24 |

Исключения, которые нельзя смешивать с этими продуктами:

- В шаблонах абонементов есть **«Пробное посещение АКВА» (B102)** и **«Разовое посещение АКВА» (B103)**. Это другие исходные продукты; в исходной классификации они проходили как `trial_or_guest`.
- В шаблонах услуг есть **«Пакет 12 ВИП (персональные тренировки)» (A25)** и **денежные сертификаты на 1000, 1500, 2000, 3000 и 5000 (A33–A37)**. Денежный сертификат не равен сертификату на месяц фитнеса.

В сохранённых каталогах Fitbase обсуждаемые пакеты АКВА и месячный сертификат также не найдены; «Пакет 12» найден среди услуг, например [ID 14](https://fitnes-imperiya.fitbase.io/services/update?id=14), а не среди абонементов. Это результат ранее собранного каталога, а не новый обход интерфейса на момент дополнительного вопроса.

Сборщик `19_build_membership_import_xlsx.py` создаёт кандидатов шаблонов из допущенных договорных строк (`template_candidates[template_key].append(template_row)`, строка 1413). Поэтому исключение этих договоров до сборщика означает также отсутствие их названий в шаблонах абонементов. Изменение числового формата шаблонов не добавляло отсутствующие продукты.
